# 도메인 뷰와 관계 패널 편집 흐름 개선

## 구현

- 도메인 선택 후 활성 보기 전환과 팝오버 닫기를 수행하는 버튼 이름을 `적용`으로 정리했다. 빈 선택과 빈 이름은 적용할 수 없다.
- 테이블 관계 패널 제목, 테이블 선택, 끝점 카디널리티, 컬럼 대응을 PK 출발 → FK 대상 순서로 정리했다. 데이터의 source(FK)/target(PK) 의미는 유지했다.
- 기존 관계 아래로 새 관계 추가 영역을 이동했다.
- 새 컬럼의 `속성명` 입력 라벨을 `속성`으로 변경했다.
- 다른 도메인 테이블 목록은 현재 도메인과 저장 도메인 뷰에 함께 포함되고 실제 물리 FK로 연결된 외부 테이블만 표시한다. 버튼과 참조 추가 핸들러를 제거하고 표시 전용 행으로 변경했다. 이미 캔버스에 표시된 참조도 목록에서 유지된다.

## 검증

- `pnpm exec vitest run apps/web/src/Canvas.test.ts apps/web/src/TableEditor.test.ts`: 17개 테스트 통과.
- 새 회귀 테스트는 저장 뷰 공동 포함/실제 FK/논리 전용 제외와 모든 관계 끝점의 PK 우선 순서를 확인한다.
- `git diff --check`: 오류 없음.
- 웹 타입 검사 시 병행 구현 중인 `document-history.js` 파일이 아직 없어 App.tsx import 오류가 발생했다. 본 변경 파일의 타입 오류는 보고되지 않았다. 통합 완료 후 재실행 필요.
- 브라우저 검증은 통합 구현 후 담당자가 수행한다.

## 브라우저 검증 완료

- 전용 격리 페이지를 사용하는 `scripts/browser-views-relations-smoke.mjs`를 추가했다. 실제 앱의 스타일과 컴포넌트를 로드하고 Chrome에서 클릭·입력으로 검증했다.
- 아무 도메인도 선택하지 않은 상태에서 적용 비활성화, 주문·결제 선택 후 적용 즉시 캔버스 2개 테이블 표시·팝오버 닫힘·현재 뷰 이름 변경·저장 문서의 domainIds 일치를 확인했다.
- 관계 편집의 테이블, 카디널리티, 컬럼 대응 모두 PK가 FK 앞에 표시됨을 DOM에서 확인했다. 기존 관계 영역이 추가 버튼보다 위에 배치됨을 실제 화면 위치로 확인했다.
- 주문 단일 도메인의 목록에는 실제 연결된 payments만 표시되고 무관한 deliveries는 제외됐다. 목록 내부에 버튼이 없고 payments 텍스트 클릭 전후 설계 문서 전체와 캔버스 테이블 개수가 동일함을 확인했다.
- 브라우저 pageerror 없음. `.cache/views-relations-order.png`, `.cache/views-relations-references.png` 결과 이미지를 생성했다. 참조 목록 이미지를 열어 표시 전용 행 배치를 확인했다.
- 병행 구현 완료 뒤 통합 웹 타입 검사가 통과했다는 결과를 담당자에게 전달받았다.
