# 대규모 fixture 조사와 실행 제한

후속: [장애물 검사 최적화](./2026-09-28-Relations-ObstacleQueries.md) 이후300개 first 제한을 통과해 warm·브라우저 측정을 수행했다. 아래 보류 결과는 변경 전 기준 기록이다.

작성일: 2026-09-28
제품 기준: `ee6e533`의 최적화된 관계 준비. 이번 단계는 제품 코드 변경 없이 측정 도구를 추가한다.

## 도구

- `pnpm perf:scale`은 50·100·300개(컬럼10개·관계1배)의 실제 `prepareTableRelations` 전체를 측정한다. 개수를 인수로 지정할 수도 있다.
- fixture 생성·진단은 측정 밖에서 실행하고, 첫 계산 시간을 별도 기록한다. 첫 계산1초 이하일 때 준비5회 후30회를 실행한다. 초과하면 `single-sample-budget` 상태로 중단하며 중앙값/p95를 만들지 않는다.
- 각 크기는 별도 Node 프로세스로 실행하고 시작부터30초 wall timeout을 둔다. 실패·timeout·출력 상한 초과는 별도 상태로 저장하며 0ms로 대체하지 않는다.
- 자식은 직접 실행하는 단일 Node 프로세스다. timeout 종료 시 출력 일부가 잘렸으면 원문과 파싱 실패 라인을 보존한다. 로그 상한은1MiB다.
- 결과는 `artifacts/performance/scale-<timestamp>/<count>.json`에 저장하며 Git 제외 대상이다. metadata에 코드 SHA·dirty·Node/OS/CPU, 제한 조건을 포함한다.
- `node --test scripts/performance/bounded.test.mjs`로 정상 종료·오류·실행 파일 없음·timeout·출력 제한·부분 JSON 보존을 검증한다.

## 사전 확인

미커밋 도구의 최초 확인에서 50개 first23ms, 100개 first96ms, 300개 first1641ms를 관찰했다. 이 결과는 도구 동작 확인용이며 최종 고정 커밋 결과는 아래에 기록한다.

사전 결정한 1초 한계를 넘은300개는 브라우저 실행과30회 반복을 보류한다. 100개까지만 브라우저의 EDIT/MOVE/PAN을 확인한다. 이는 300개를 지원할 수 없다는 결론이 아니라 현재 동기 계산의 긴 작업 위험을 근거로 한 조사 중단 조건이다.

## 사용

```powershell
node --test scripts/performance/bounded.test.mjs
pnpm perf:scale
pnpm perf:scale 100
```

Node 시간은 브라우저 표시 지연이나 전체 사용자 입력 지연이 아니다. fixture 하나의 전체 관계 준비 비용이며 layout/paint·전송·협업은 포함하지 않는다. 첫 계산이 반복보다 느리거나 빠를 수 있으므로 first와 warm 통계를 섞지 않는다.

## 고정 커밋 계산 결과

측정 코드 `6b57367`, dirty=false에서 부모 실행3회, 크기별 별도 자식 프로세스로 실행했다. Node v24.18.1, Windows, Ryzen9 7900X. 각 크기의 첫 계산을 별도 기록하고, 50/100개는 준비5회+측정30회를 각각 수행했다.

| 크기 | 독립 실행별 중앙값 | 독립 실행별 p95 | 첫 계산 |
| --- | --- | --- | --- |
| 50개 | 21.04 / 21.05 / 20.94ms | 23.78 / 23.15 / 22.24ms | 24.16 / 23.04 / 22.66ms |
| 100개 | 110.61 / 110.60 / 81.77ms | 113.96 / 113.44 / 84.23ms | 94.06 / 93.92 / 93.62ms |
| 300개 | 미측정 | 미측정 | 1634.58 / 1638.91 / 1634.21ms |

100개는 실행 간 변동이 있어 평균 하나로 축약하지 않았다. 300개는 모든 독립 실행에서 first budget을 초과해 `single-sample-budget`으로 종료했다. 프로세스 자체는 정상 종료했고 timeout crash가 아니다. 300개의 세 first 표본을 warm p95로 표현하지 않는다.

원시 파일 디렉터리: `artifacts/performance/scale-1790590046519/`, `scale-1790590055946/`, `scale-1790590065473/`. 각 폴더의50/100/300.json에 metadata·원시값·제한 판정을 보존했다.

## 100개 브라우저 결과

동일 커밋의 production 계측 빌드, in-app browser, viewport1440×900, locale ko, 테이블100·컬럼10·관계100을 사용했다. EDIT/MOVE는 각 준비1회+반복3회, PAN은3회 수행했다. 입력과 최종 문서 값은 기존 helper로 검증했다.

| 조작 | 카드 치수 호출 | 관계 경로 호출 | 치수 누적 시간 범위 | 경로 누적 시간 범위 |
| --- | --- | --- | --- | --- |
| EDIT | 300 | 100 | 9.4~11.1ms | 97.7~101.9ms |
| MOVE (pointermove4개) | 1,200 | 400 | 45.0~46.3ms | 424.6~441.5ms |
| PAN (wheel1개) | 0 | 0 | 실행 없음 | 실행 없음 |

시간은 run 내부 함수 inclusive 누적값이며 자동화 대기·전체 입력 지연·paint 시간과 다르다. PAN은 문서 불변과 카메라 이동을 확인했고 `assertCameraReuse`가3회 모두 통과했다. 브라우저 error 로그는 없었다.

원시 결과·SVG paths·환경은 `artifacts/performance/6b57367-browser/`에 저장했다. 화면 증거는 `scale-100.png`다. 산출물은 Git 제외 대상이며 문서 요약은 커밋한다.

## 판단과 다음 우선순위

- 팬 최적화는100개에서도 유지됐다. 반면 문서 편집/이동 시 전체 관계 탐색 비용이 치수 계산보다 크게 남았다.
- 300개 동기 관계 준비는 첫 표본1.6초 수준이므로 이번에는 브라우저를 열어 반복하지 않았다. 다음에는 관계 탐색 입력·장애물 후보 축소 또는 변경 영향 범위 제한을 조사하고 이 사전 검사를 다시 통과시키는 것이 우선이다.
- 300개에서 애플리케이션이 crash한다거나 렌더러가 원인이라는 증거는 없다. 초기 표본은 순수 관계 준비 계산이며 GPU·DOM·React 비용은 제외됐다.
- 컬럼30개·관계3배, 300개 warm/UI, 장시간 메모리, 프레임/입력 지연 trace는 미측정이다. 이번 결과로 그 범위의 성능을 일반화하지 않는다.

## 검증·정리

- bounded runner 테스트4개, 포맷 검사와 diff 검사 통과. 실제 `perf:scale` 고정 커밋3회 및 `perf:build` 성공으로 실행 경로·타입·빌드를 확인했다.
- 제품 코드 변경이 없어 전체 제품 테스트는 반복하지 않았다. 이전 단계의381개 통과 이력을 이번에 다시 실행한 결과로 표시하지 않는다.
- 테스트 탭과 fixture 서버를 종료한다. 로컬 성능 브랜치에만 기록하며 원격 push·main 병합은 수행하지 않는다.
