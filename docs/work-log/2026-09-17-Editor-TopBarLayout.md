# 편집기 상단바 배치 개선 작업 기록

기록일: 2026-09-17

계획: [편집기 상단바 배치 개선 계획](../planning/2026-09-17-Editor-TopBarLayout.md)

계획 문서에서 집계한 UI 이슈 8건을 구현했다. 데이터·모델 쪽 2건(조합 뷰 관계선 경로 삭제, 조합 뷰 단수 고정)은 이번 범위가 아니다.

## 1. 처리한 이슈

| 이슈 | 처리 |
| --- | --- |
| 균일한 간격 | `editor-topbar.css`에서 간격을 두 단계로 나눴다. 그룹 안은 4px, 그룹 사이는 `clamp(10px, 1vw, 14px)`, 영역 사이는 `clamp(16px, 2vw, 28px)`다. 도구 사이 간격은 구분선이 `margin-inline`으로 담당한다. |
| 짝이 갈라진 토글 | 핀 버튼을 `save-controls`에서 캔버스 도구의 `panel-toggles` 그룹으로 옮겨 속성 패널 토글과 나란히 뒀다. 둘 다 같은 크기의 아이콘 버튼이며 `aria-pressed`로 상태를 표시한다. |
| 떨어진 생성 버튼 | `＋ 도메인`·`＋ 테이블`과 `＋ 메모`를 한 그룹으로 붙이고, 도메인 뷰·ENUM·고화질 PNG는 구분선 뒤 별도 그룹으로 분리했다. |
| 과하게 강조된 브레드크럼 | `← 도메인 맵으로` 강조 버튼을 없애고 경로 단계로 바꿨다. `styles.css`의 `.domain-map-return` 규칙도 함께 삭제했다. |
| 뷰별 폭 흔들림 | 경로를 왼쪽 영역으로 옮겨 도구 영역에서 분리하고, 도메인 맵에서 숨어 있던 ENUM을 항상 노출해 슬롯 수를 8개로 고정했다. 도메인 맵과 도메인 뷰에서 도구 영역의 시작 좌표가 981px로 같다. |
| 소유 컴포넌트 3분할 | `App.tsx`가 영역과 슬롯을 소유하고 `Canvas`는 내용만 전달한다. 경로는 `pathHost` portal로, 핀 토글은 `panelToggle` prop으로 주고받는다. |
| 조합 뷰 이름 고정 | `combinedViewName`이 포함 도메인 이름으로 뷰 이름을 만든다. 4개 이상이면 앞의 두 개와 남은 개수로 줄이고 120자를 넘지 않는다. |
| 논리·물리 전환 잔재 | `inspector.css`의 `.view-mode-switch` 규칙 세 벌과 전환 목록의 참조를 제거했다. |

## 2. 최종 배치

| 영역 | 내용 |
| --- | --- |
| 왼쪽 | `← 갤러리`, 프로젝트명, `/ 도메인 맵 / 현재 뷰` 경로 |
| 가운데 | `↶ ↷`, 동기화 상태, `히스토리` |
| 오른쪽 | 생성 그룹 · 뷰와 리소스 그룹 · 패널 토글 그룹 |

계획 문서는 가운데를 생성, 오른쪽을 문서 상태로 적었으나 `editor-feedback.css`가 `order`로 캔버스 도구를 이미 오른쪽 끝에 배치하고 있었다. 기존 배치를 존중해 가운데와 오른쪽의 역할을 맞바꿨다. 영역마다 하나의 질문에 답한다는 원칙은 그대로다.

장식용 `PROJECT / DOMAIN WORKSPACE` 오버라인을 제거해 왼쪽 영역이 한 줄이 됐다.

## 3. 도메인 뷰 상태 표시

같은 버튼이 도메인 맵에서는 조합 뷰 진입으로, 조합 뷰 안에서는 포함 도메인 변경으로 동작한다. 상태를 두 곳에서 드러낸다.

- 버튼 라벨이 `도메인 뷰`에서 `도메인 구성`으로 바뀌고 `is-active` 배경을 사용한다.
- 경로의 현재 단계 앞에 버튼과 같은 목록 아이콘을 강조색으로 표시하고 `title`에 `(도메인 뷰)`를 덧붙인다.

## 4. 기존 분위기 유지

- 공통 `Button`·`IconButton`을 그대로 쓰고 새 버튼 컴포넌트를 만들지 않았다.
- 아이콘은 속성 패널 토글과 같은 20 viewBox 선 아이콘으로 맞췄다.
- 활성 상태는 기존 `[aria-expanded='true']`와 같은 인셋 뉴모피즘 그림자를 사용한다.
- 전환은 160ms ease, 경로 진입은 `enum-content-enter`와 같은 결의 180ms ease-out이며 `prefers-reduced-motion`을 따른다.
- 경로의 현재 단계에 `key={viewId}`를 줘서 `.canvas-column`의 뷰 전환 연출과 같은 시점에 동작한다.

## 5. 새 스타일시트를 만든 이유

상단바 규칙을 `apps/web/src/editor-topbar.css`에 모으고 `main.tsx`에서 마지막에 불러온다. `editor-feedback.css`·`canvas-viewport.css`와 같은 관심사별 파일 방식을 따랐고, `responsive-shell.css`에 커밋되지 않은 변경이 있어 커밋이 섞이지 않게 하려는 목적도 있다.

## 6. 검증

- `pnpm typecheck`, `pnpm test`(288건 통과·20건 건너뜀), `pnpm format:check` 통과.
- 메모리 API 픽스처로 1512×827에서 확인했다. 상단 행 높이가 64px에서 47px로 줄어 캔버스 시작점이 약 17px 올라갔다.
- 1920×1080부터 390×844까지 8개 너비에서 가로·세로 넘침이 모두 0이다. 390px에서만 도구가 여러 줄로 접힌다.
- 도메인 맵과 도메인 뷰에서 도구 영역 시작 좌표가 981px로 같고 슬롯 수가 8개로 유지된다.
- 조합 뷰 적용 후 버튼이 `도메인 구성`으로 바뀌고 경로에 목록 아이콘이 표시되며 `＋ 테이블`이 비활성으로 남는 것을 확인했다.
- 브라우저 오류·경고 로그가 없고 실제 DB 데이터는 변경하지 않았다.

QA 픽스처가 `main.tsx`를 거치지 않고 스타일시트를 직접 나열하고 있어 새 파일이 빠졌다. `scripts/prepare-editor-feedback-qa.mjs`에 `editor-topbar.css`를 추가하고 픽스처를 다시 만들었다.

## 7. 남은 작업

- 계획 문서의 남은 결정 세 가지 가운데 오버플로 메뉴 도입 여부는 아직 정하지 않았다. 도입하면 `고화질 PNG`와 `ENUM`이 후보다.
- `responsive-shell.css`에 남은 상단바 규칙을 `editor-topbar.css`로 모으는 정리가 필요하다. 지금은 두 파일이 같은 행을 나눠 담당한다.
- `styles.css`와 `responsive-shell.css`의 `.breadcrumbs` 규칙은 더 이상 사용하지 않는다. 정리 시점을 따로 잡는다.
- 데이터 쪽 이슈 두 건(조합 뷰 관계선 경로 삭제, 조합 뷰 단수 고정)은 그대로 남아 있다.
