개별 컬렉션 값의 직렬화 크기이며 최상위 키/구분자 및 DB 문맥 등이 총합 차이를 이룬다. 테이블 관계 254개 중 247개는 both, 7개는 logical이다. 앞선 물리 화면 진단의 247개와 차이는 이 때문이다.

## 컬럼 상세

- physical 값 합계 440,945바이트: type 149,177, defaultValue 49,411, options 40,675, generation 24,449, name 24,244, comment 13,506 등이 포함된다.
- logical 값 합계 138,901바이트. 1,616개 컬럼에서 논리명과 물리명이 동일하다. 물리 comment가 빈 컬럼 1,298개, 논리 definition이 빈 컬럼 1,186개다.
- 컬럼 id 값 합계 73,162바이트, tableId 값 합계 69,513바이트. 문자열 값 크기이며 필드 키 구문은 별도다.
- customProperties 값 합계 69,404바이트. 1,488개 컬럼은 common/logical/physical이 전부 빈 객체다. 해당 빈 customProperties 필드를 생략하는 가상 실험에서 정확히 89,280바이트(6.19%) 줄었다. 현재 계약은 필수이므로 실제 삭제는 하지 않았으며, 저장 표현 변경 및 읽기 기본값 복원이 선행되어야 한다.
- 위 값별 합계는 각 속성 값의 JSON 크기다. 속성명·쉼표·괄호도 반복 저장되므로 상위 컬렉션 크기와 직접 일치하지 않는다.

## 메타데이터와 경로

- 테이블 customProperties 필드 전체 비용 42,566바이트, 컬럼 전체 101,944바이트(키/구분자 포함 제거 전후 비교). 모두 제거하면 정보 손실이 있으므로 절감 권장이 아닌 측정값이다.
- 대표 메타데이터 값: sqlCatalog 10,509바이트, checkSql 7,013바이트, stage 3,698바이트, source 3,500바이트, defaultSql 2,418바이트. 거대한 단일 SQL/메모가 원인은 아니다.
- 가장 큰 개별 객체는 tbl_workspace_attendees 테이블 3,371바이트다(컬럼은 별도 컬렉션). 100자 초과 customProperties 값의 완전 동일 반복은 발견되지 않았다. 다만 짧은 DB 문맥·빈 구조의 반복은 많다.
- layout.nodes 35,965바이트, layout.relations는 빈 배열 2바이트, viewports 44바이트다. 현재 원본에 저장된 관계선 경로는 0개다.
- 앞선 자동 정리 후보는 1,506,456바이트로 63,970바이트 증가했다. 현재 1.5MB 한도를 6,456바이트 초과한다. 관계선만 분리해도 현재 원본의 크기 증가 문제를 근본 해결하지 못한다.

## 판단 자료

우선 검토할 후보는 빈/기본 필드의 저장 생략과 읽기 복원, 타입·DB 문맥 반복을 줄이는 저장 표현이다. 논리/물리 이름 중복은 서로 독립 편집 의미가 있으므로 단순 삭제하지 않는다. 배치 별도 저장은 편집 성능 측면에서 별도로 검토할 수 있지만 현재 용량의 주범은 컬럼이다. 사용자 결정 전 구현·정책 변경은 하지 않았다.
