# 기존 UI를 보존하는 캔버스 이동 성능 비교 결과

- 날짜: 2026-10-02
- [계획](../planning/2026-10-02-Performance-CanvasSmoothness.md) / [계측 구현](2026-10-02-Performance-CanvasComparisonInstrumentation.md)
- 제품 기준: main 396ba24를 병합한 격리 lab. 최종 측정 빌드: 9d40fab, dirty=false.
- 범위: 두 캔버스의 읽기 전용 이동 비교와 원인 분리 실험. 제품 코드를 최적화하거나 기존 UI를 Native에 이식한 단계는 아니다.

## 결론

이번 조건에서는 기존 카드·관계선 하위 React 트리의 반복 갱신을 억제하는 것이 가장 효과적이었다. 기존 화면의 DOM 요소 8,102개와 SVG path 1,250개를 그대로 유지하면서 React 렌더 중앙값이 10.9ms에서 1.2ms로 약 89% 감소했다. 프레임 간격 중앙값/p95는 30/40ms에서 10/20ms로 줄어 같은 테스트의 Native와 비슷해졌다.

따라서 기존 화면의 시각 요소를 없애야만 Native 수준의 부드러움에 도달한다는 가설은 이 실험에서 지지되지 않는다. UI 보존형 렌더 경계 분리를 먼저 진행하는 것이 적절하다. 전체 제품·실제 운영 문서의 가장 큰 병목이라고 일반화하지 않는다.

## 방법과 재현 조건

- 결정적 50테이블, 테이블당 10컬럼, 관계 50개. 같은 v1 fixture를 메모리에서 v2로 변환하며 ID/배치를 공유한다. 실제 DB 접근은 없다.
- viewport 1440×900, DPR 1, 양쪽 canvas surface 1440×520, 초기 카메라 translate(24px,24px) scale(1).
- Chrome 154 계열 in-app browser. 유휴 rAF 중앙값은 약 10ms였다. 60Hz 환경이나 다른 PC의 절대 FPS로 환산하지 않는다.
- 주변 상세 패널은 비교 영역에서 제외한다. Native와 기존 카드의 실제 크기·내부 표현·관계 라우팅은 각 구현을 유지한다. 앱 전체나 기능 동등성 비교가 아니다.
- 유한 mount 애니메이션 종료, 폰트 준비, 8회 이동 warm-up, 20개 idle frame 뒤 측정한다.
- 프레임당 합성 wheel 1개, +4px 60회와 -4px 60회. 각 조건 1회 준비 실행 후 3회 측정, 두 번째 반복은 순서를 뒤집었다.
- 표의 중앙값과 p95는 각 실행에서 계산한 값의 3회 중앙값이다. 25ms 초과 수는 3회 합계다.
- production React profiling 및 함수 span 계측이 활성화된 진단 빌드다. 일반 production 절대 성능으로 해석하지 않는다. Native는 함수 span 수가 더 많아 계측 오버헤드도 동일하지 않다.

| 기존 원본 | 10.9 / 14.8 | 30 / 40 | 313 | 8,102 |
| Native 원본 | 8.8 / 10.3 | 10 / 20 | 0 | 3,004 |

| 기존 관계선 렌더링 제외 | 11.0 / 15.3 | 30 / 30.1 | 232 | 7,302 |

카드 제목만 남기는 조건은 원인 확인용이며 채택할 제품 변경이 아니다. 관계선 제외는 body/control 컴포넌트를 모두 생략하지만 장면의 geometry 준비까지 제거하지 않는다. flat-style은 box-shadow/text-shadow/filter/backdrop-filter만 제거하며 모든 paint 비용을 제거한 조건이 아니다. SVG path 수에는 카드 내부 아이콘도 포함되어 관계선 개수와 같지 않다.

## React와 브라우저 비용 해석

- 기존 캔버스는 카메라만 움직일 때 이미 기하 계산을 재사용한다. 그럼에도 카드와 관계선 React 하위 트리는 갱신된다.
- memo-leaves는 TableNodeContent와 TableRelationsSvg의 변경되지 않은 입력을 재사용한다. 원본과 같은 요소·텍스트·스타일을 유지하면서 큰 차이가 났으므로 React 갱신 경로는 강한 개선 후보다.
- 카드 축소에서도 비슷한 개선이 발생하고 관계선만 제외하면 React 시간이 크게 줄지 않았다. 카드 하위 트리의 기여가 크다는 근거다. 카드-only memo 대조를 별도로 수행한 것은 아니므로 두 컴포넌트의 정확한 기여율은 미확정이다.
- Native의 중복 scene 계산은 여전히 존재하지만 그 사실만으로 기존보다 느리다고 결론 내릴 수 없다. 현재 실측은 Native가 더 짧은 프레임 간격을 보인다는 사용자 관찰과 일치한다.
- Profiler actualDuration은 React 렌더 시간이며 DOM commit/브라우저 layout/paint/GPU 시간을 전부 포함하지 않는다. rAF 간격에서 이를 빼서 paint 시간이라고 부르지 않는다.
- longtask/Long Animation Frame 관측기를 지원했으나 본 측정 18개 실행에서는 관측 항목이 없었다. 추가 준비 실행 legacy-baseline-0에서는 longtask와 Long Animation Frame이 각 1개 기록됐다. 50ms 초과 장기 작업 중심 API이므로 layout/paint의 정확한 비율을 분해할 근거는 부족하다. 이 측정은 DevTools trace를 대체하지 않는다.

## 실제 브라우저 입력 확인

합성 재생과 별도로 브라우저 실제 wheel 명령을 각 조건 6회 입력했다. 모든 조건은 문서를 변경하지 않고 카메라가 (24,24)에서 (-96,24)로 이동했다.

| 조건 | wheel / React commit | React 중앙값(ms) |
| --- | --- | --- |
| 기존 원본 | 6 / 6 | 12.6 |
| Native 원본 | 6 / 7 | 9.7 |
| 기존 leaf 재사용 | 6 / 6 | 1.5 |

이 표는 동작 및 개선 방향 확인용이다. 도구 호출 간 유휴 시간이 있어 연속 입력 FPS 벤치마크로 사용하지 않는다. React commit 수는 이벤트와 반드시 1:1이 아니며 합성 실행에서도 119~120회가 관측됐다.

## 최종 구현에 가져갈 원칙

1. 카메라 shell과 문서 scene을 분리한다. pan/zoom은 transform과 카메라 UI만 변경하고 테이블 내용 및 관계선 JSX를 재구성하지 않게 한다.
2. 기존 카드의 헤더, 컬럼·키 표시, 인라인 편집, 관계선 스타일을 표현 컴포넌트로 분리한다. Native의 타입·기본값 모델을 v1로 축약해 기존 컴포넌트에 강제로 넣지 않는다.
3. 문서별 표시 데이터/조회 인덱스를 준비하고 카드에는 필요한 데이터와 안정적인 액션을 전달한다. hover/편집 상태는 해당 카드 또는 편집 overlay에 국한한다.
4. 콜백을 무시하는 진단용 memo 비교기를 제품에 복사하지 않는다. 최신 문서/선택/권한을 반영하는 정상적인 props와 callback 계약을 만들고 React 기본 비교로 재사용할 수 있게 한다.
5. 기존 UI를 카드 표현 → 관계선 표현 → 선택/hover → 편집 컨트롤 순으로 복원하며 단계마다 이동 baseline을 비교한다. 기능을 끄거나 스타일을 줄이는 것으로 성능 기준을 맞추지 않는다.
6. Native 중복 scene 계산 제거와 문서 인덱스 공유는 그다음 병행 가능하다. 먼저 렌더 경계를 확정해야 UI를 가져올 때 같은 문제가 재발하지 않는다.

## 다음 구현의 검증 기준

- camera-only 입력에서 카드 내용·관계선 경로 재계산이 발생하지 않는지 확인한다.
- 동일 기기/문서/입력의 일반 production 빌드에서 Native 기준 대비 frame p95가 유의하게 나빠지지 않는지 반복 검증한다. 이번 10ms를 모든 환경의 고정 목표로 삼지 않는다.
- 문서 변경, 컬럼 편집, 선택, FK 생성/편집, 키보드 조작, 드래그 종료 좌표, 권한·프로젝트 전환을 검증한다. 특히 카메라 이동 후 편집이 오래된 문서에 적용되지 않아야 한다.
- read-only pan 실험은 편집·접근성·협업 기능 동등성을 보증하지 않는다. 최종 UI 통합 전에 별도 회귀 검증이 필요하다.
