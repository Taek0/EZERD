# UI 전체 구성 검토 결과

## 결론

캔버스 중심 편집기와 우측 속성 패널, 별도 갤러리라는 기본 구조는 유지하는 편이 좋다. 개선의 우선순위는 모바일 패널 잘림 해결, 도구의 역할과 우선순위 구분, 반복 탐색 동선 단축이다. apple-design 스킬의 단순성·주도권·정보 위계·공간 일관성을 기준으로 검토했으며, 유리 효과나 바운스 추가를 목표로 삼지 않았다.

- 날짜: 2026-10-11 (Asia/Seoul)
- 기준: `64542f7`, 브랜치 `codex/apple-ui-review`
- [계획](../planning/2026-10-11-UI-CompositionReviewPlan.md)
- [이전 인터랙션·대비 검토](2026-10-11-UI-AppleDesignReview.md)
- 제품 UI 코드는 수정하지 않았다.

## 검토 방법과 범위

실제 NativeProjectView를 기존 테스트 fixture의 두 테이블과 한 도메인으로 렌더링했다. 테스트 데이터의 테이블·컬럼 scope를 both로 설정하고 편집 권한을 제공했다. 세션과 API 응답은 localhost 검토 화면 안에서 생성한 가짜 데이터이며, fetch를 대체해 제품 서버로 요청하지 않았다. 앱 모듈을 먼저 불러온 뒤 main.tsx와 같은 순서로 공통 스타일을 로딩했다.

브라우저에서 1440×900, 1024×768, 390×844 크기를 확인하고, 속성·핀 패널 동시 열기와 목록에서 테이블 선택을 수행했다. 갤러리는 이전 실제 컴포넌트 검증과 이번 소스 구조 확인을 결합했다.

상단 계정·워크스페이스 헤더는 축약한 테스트용이다. projectActions를 전달하지 않아 내보내기는 실제 App의 공유 메뉴 대신 컴포넌트의 PNG fallback을 표시했다. 따라서 도구 줄 높이 수치는 이 fixture 조건의 측정값이며 전체 운영 앱의 픽셀 단위 측정으로 일반화하지 않는다. 캔버스의 fixture 카드 겹침도 제품 결함으로 분류하지 않는다.

## 1. [P2 · 확인된 결함] 좁은 화면에서 속성 본문이 잘린다

- 재현: 390×844 → 테이블 선택 → 속성 패널과 핀 패널을 모두 연다.
- 관찰: 전체 가로 넘침은 없지만 캔버스는 약 182px 높이로 축소된다. 속성 패널은 약 304px 높이를 요구하는데 실제 grid 두 번째 행은 약 121px만 할당한다. 패널 헤더만 보이고 입력 본문은 부모의 overflow 영역 밖으로 잘린다.
- 측정: editor workspace y=321.25, 높이 약303.31, grid rows 약182/121.31px. 속성 패널 y=503.25, 높이 약303.83px, 본문 y=660.25. 부모의 표시 영역은 y≈624.56에서 끝나므로 본문 시작점부터 보이지 않는다. 같은 위치 아래에 핀 패널이 배치된다.
- 원인 근거: [inspector.css](../../apps/web/src/styles/inspector.css) 14–16행의 `height: clamp(240px, 36dvh, 340px)`와 [native-project-view.css](../../apps/web/src/features/projects/native-project-view.css) 330–332행의 두 번째 grid 행 `min(40%, 240px)`가 충돌한다. native workspace는 같은 파일 46–51행에서 overflow를 숨긴다. 핀 패널은 [comments.css](../../apps/web/src/features/comments/comments.css) 642–656행에서 하단 높이를 추가로 확보한다.
- 우선 수정: native stacked inspector의 높이를 grid 행에 맞추고 내부 본문만 스크롤되게 한다. 모호한 기존 `.inspector` 전역 높이 규칙과 native 레이아웃의 책임을 분리한다.
- 구성 개선: 좁은 화면에서는 `캔버스 / 속성 / 핀` 중 한 작업 영역을 선택하거나, 필요한 보조 패널만 명시적으로 여는 바텀시트를 검토한다. 사용자가 두 패널을 동시에 열었는데 내용이 사라지는 상태는 허용하지 않는다.
- 완료 조건: 세 가지 크기에서 모든 필드와 닫기 동작에 접근할 수 있고, 각 스크롤 영역과 실제 표시 영역이 일치한다. 실제 터치 기기와 가상 키보드도 후속 검증한다.

## 2. [높은 개선 우선순위 · 디자인 제안] 상단 도구를 역할별로 구분한다

현재 생성(테이블·메모), 보기 전환(전체 테이블·도메인 맵), 필터, ENUM 관리와 패널 토글이 한 줄의 비슷한 입체 버튼으로 표현된다. 구분선과 선택 상태는 있으나 작업 종류를 빠르게 훑기는 어렵다. 일부 주요 버튼을 모두 88px로 맞춘 규칙은 일관성을 주지만 공간과 우선순위 표현을 제약한다.

- 근거: [NativeCanvasToolbar.tsx](../../apps/web/src/features/projects/NativeCanvasToolbar.tsx) 154행 이후, [native-project-view.css](../../apps/web/src/features/projects/native-project-view.css) 369행 이후.
- 관찰: fixture의 editor-heading은 1440px에서 약110px, 390px에서는 약260px를 차지했다. 모바일에서 상단 영역과 여러 패널이 경쟁하는 구조다.
- 제안: `전체 테이블 / 도메인 맵`을 하나의 보기 선택 컨트롤로 묶고, 생성은 명확한 `추가` 그룹으로, ENUM 등 보조 관리는 메뉴로 묶는다. 필터는 활성 개수와 상태를 표시한다. 생성, 선택, 설정을 모두 같은 강도로 강조하지 않는다.
- 프로젝트명·현재 위치·저장 상태는 안정적인 위치를 유지한다. DB 종류·버전·편집 권한은 상세 정보 팝오버로 줄일 수 있다.
- 좁은 화면에서는 버튼 줄바꿈만 반복하기보다 노출할 핵심 동작 수를 정한다.

## 3. [중간 개선 우선순위 · 디자인 제안] 목록에서 연속 탐색할 수 있게 한다

실제 UI에서 `목록 2` → `audit`를 선택하자 탭이 즉시 `속성`으로 바뀌고 목록이 사라졌다. 여러 테이블을 비교하거나 빠르게 훑는 사용자는 매번 목록 탭을 다시 열어야 한다. 이번 마우스 클릭 검증에서는 포커스도 페이지로 돌아갔다. 키보드 사용성은 별도 회귀 검증이 필요하다.

- 근거: [NativeProjectView.tsx](../../apps/web/src/features/projects/NativeProjectView.tsx) 1638행 이후의 탭 구성, 1896행의 `setInspectorTab('properties')`.
- 제안: 넓은 화면에서는 접을 수 있는 탐색 목록과 선택 속성을 분리하는 옵션을 제공한다. 중간 크기에서는 현재 구조를 유지하면서 속성 상단에 테이블 선택/검색과 이전·다음 이동을 제공할 수 있다. 좁은 화면에는 추가 상시 패널을 만들지 않는다.
- 목록에서 속성으로 전환할 때는 선택한 대상 제목 또는 첫 편집 컨트롤로 포커스를 명시적으로 옮긴다.
- 유지할 점: 현재 화면 범위 검색, 도메인 필터, 선택 객체 표시와 속성 섹션 접기는 유용하다.

## 4. [중간 개선 우선순위 · 디자인 제안] 프로젝트 생성 버튼을 항상 찾을 수 있게 한다

갤러리의 제목·소개 영역과 196px 미리보기는 처음 보는 사람에게 공간감을 주지만, 프로젝트가 많아지면 반복 작업에 비해 세로 공간을 많이 쓴다. 눈에 띄는 새 프로젝트 카드는 기존 카드 목록 뒤에 나오고, 상단 생성 동작은 `⋯` 메뉴 안에 있다.

- 근거: [project-gallery.css](../../apps/web/src/features/projects/project-gallery.css) 1–24, 173–175행, [ProjectGallery.tsx](../../apps/web/src/features/projects/ProjectGallery.tsx) 400행 이후 메뉴와 517행 이후 새 프로젝트 카드.
- 제안: 검색·정렬과 같은 도구 영역에 텍스트가 있는 `＋ 새 프로젝트`를 둔다. 가져오기·부가 동작은 메뉴에 유지한다. 새 프로젝트 카드는 빈 상태에서 특히 강조한다.
- 프로젝트가 있는 상태에서는 소개 문구를 축약하거나 컴팩트/목록 보기를 제공한다. 이름·DB·최근 수정·규모를 먼저 읽을 수 있게 한다.
- 목록이 긴 실제 사용자 환경의 작업시간 측정은 하지 않았으므로 생산성 효과는 가설이다. 기존 카드 보기를 무조건 없애자는 제안은 아니다.

## 5. [중간 개선 우선순위 · 디자인 제안] 주요 모드와 확인 필요 상태를 발견하기 쉽게 한다

논리 설계 활성화와 설계 확인 항목은 `더 보기` 메뉴에 있다. 논리·물리 설계와 검증 상태는 제품의 핵심 개념이므로, 처음 사용하는 사람은 존재를 모르거나 확인을 놓칠 수 있다.

- 근거: [NativeCanvasToolbar.tsx](../../apps/web/src/features/projects/NativeCanvasToolbar.tsx) 236–263행. 설계 이슈가 있어도 상시 목록을 숨기는 동작은 `NativeProjectView.test.ts`에서도 명시한다.
- 제안: 논리 설계를 사용하는 프로젝트에는 현재 모드와 전환 위치를 직접 보여준다. 검증 항목은 존재할 때만 `확인 필요 N` 배지를 노출한다. 저장 실패 상태와 설계 미완성 상태는 구분한다.
- 관찰 범위: 메뉴 구조는 코드로 확인했다. 비어 있지 않은 설계 이슈 목록을 브라우저로 재현하지는 않았다. 결함 판정이 아닌 발견 가능성 개선 제안이다.

## 유지할 구성

- 편집과 협업을 캔버스 옆에서 수행하고, 패널을 닫거나 크기를 조절할 수 있다.
- 1440×900에서 속성과 핀을 함께 열어도 fixture의 캔버스 폭은 약794px로 남았다. 기본 데스크톱 배치는 작업 공간을 확보한다.
- 1024×768에서는 핀이 하단으로 이동하고 캔버스는 약698×413px를 유지했다. 실제 문서 가로 넘침은 없었다.
- 선택 객체의 이름과 종류, 현재 보기, 저장 상태가 존재한다.
- 기본 정보·컬럼과 고급 옵션을 나누고 섹션을 접는 구조는 유지한다.
- 캔버스 하단의 커서·손 도구·배율 컨트롤은 조작 대상 가까이에 있다.

## 권장 구성안

| 영역 | 기본 내용 | 공간 부족 시 |
| --- | --- | --- |
| 전역 헤더 | 워크스페이스, 사용자, 알림 | 명칭 축약과 보조 메뉴 |
| 문서 바 | 갤러리, 프로젝트명, 현재 보기, 저장 상태·이력 | DB 상세는 정보 팝오버 |

| 갤러리 도구 | 검색, 정렬, 새 프로젝트 | 새 프로젝트 텍스트 진입점 유지 |

## 권장 진행 순서

1. 속성 패널 잘림과 이전 검토의 텍스트 대비·재열기 입력 누락을 수정한다.
2. 상단 도구 역할 구분과 갤러리 새 프로젝트 진입점을 정리한다.
3. 목록 연속 탐색과 논리/물리 모드·검증 상태의 발견 가능성을 개선한다.
4. 실제 큰 ERD와 많은 프로젝트, 모바일 키보드 환경에서 재검증한다.
