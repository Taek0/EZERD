# 최신 히스토리 조회·성능·스크롤 수정

## 원인

- 기존 UI는 since=0부터 오름차순 25개를 읽고 그 페이지 내부만 역순 표시했다. klassboard-backend에는 261~329번 69개가 남아 있었지만 처음 표시한 페이지는 261~285번이었다. 더보기로 뒤 페이지를 받아야 최신 항목이 나타났다.
- 각 이력 result에 저장 당시 전체 설계 document와 delta가 포함됐다. 첫 25개 result JSON만 13,550,124바이트였고, 별도로 changes가 154,999바이트였다. undo 컨트롤도 여러 페이지를 순차 조회했다.
- popover/list/변경 설명의 중첩 스크롤이 휠 동작을 나누고 있었다.

## 변경

- HTTP 이력 조회에 order=desc, exclusive before 및 nextBefore를 추가했다. 기존 since/nextSince 오름차순 API와 MCP 소비자는 유지한다.
- 웹은 compact=true로 조회한다. SQL 단계에서 result.document/delta와 불필요한 삭제 문서 payload를 제외하며 undo 판정에 필요한 nativeHistory 메타데이터는 유지한다. DB 이력 원문과 undo/restore 검증은 변경하지 않는다.
- 패널은 최신 25개부터 표시하고 더보기는 과거를 추가한다. 최신 sequence 갱신 시 중복 없이 병합하고 이미 읽은 과거 페이지는 겹치는 구간이 있을 때 유지한다. 구간이 끊기면 커서를 재설정한다. 계정/프로젝트 변경 및 오래된 응답은 abort로 격리한다.
- 초기 로딩·실패·재시도 상태를 표시하고 설명 생성 결과를 메모이제이션한다. undo 조회는 100개 단위로 요청해 연속 25개 요청을 줄인다.
- 히스토리 스크롤은 외부 popover/dialog 하나로 통합하고 휠은 기본 스크롤을 유지하며 상위 이벤트 전파만 막는다. 히스토리 버튼과 화살표 사이에 8px 간격을 추가했다.

## 검증

- 같은 사용자 읽기 권한으로 같은 프로젝트의 새 서비스 조회를 실행했다. 첫 페이지 329~305번, 전체 응답 83,606바이트, 로컬 서비스 조회 약 75ms였다. 브라우저 전체 로딩 시간 측정은 아니며 실제 사용자 문서는 수정하지 않았다.
- 임시 PostgreSQL에 55개 이력을 생성해 최신/과거 페이지 누락·중복 없음, compact payload, 원문 유지, 오름차순 호환 및 타 사용자 접근 거부를 검증했다. 테스트 DB만 생성·삭제했다.
- 독립 실제 Chromium에서 최신 65번이 첫 행에 표시되고, 휠 입력으로 스크롤이 0→330px 이동함을 확인했다. 가짜 API를 사용해 사용자 프로젝트와 분리했다.
- 전체 회귀 테스트 3,007개 통과 / 환경 의존 500개 건너뜀. 이후 추가한 커서 경계 검증을 포함한 계약·수명주기 14개 재검증 통과. 계약/서버/서버 도구/웹 타입, Prettier, 웹 빌드 통과. 기존 번들 경고 유지.
- DB 스키마 변경이나 마이그레이션은 없다. 새 서버 API와 웹을 함께 재빌드·재시작해야 한다. 검증용 브라우저/서버/페이지는 정리했다.
