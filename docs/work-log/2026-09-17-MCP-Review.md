# MCP 구현 직접 검토 기록

작성일: 2026-09-17

## 역할과 범위

- 사용자 요청에 따라 구현은 `gpt-5.6-sol`, reasoning `medium` 서브 에이전트가 수행했다.
- 주 에이전트가 코드, 인증 경계, 동기화 규칙, 브라우저 화면과 실제 HTTP 호출을 직접 검토했다.
- 검토 대상 구현 커밋은 `4477b27`부터 `c5f1d7c`까지다. 계획은 `docs/planning/2026-09-17-MCP-LanHosting.md`를 따른다.

## 검토 중 발견하여 반영한 사항

- 서비스 추출 이후에도 인증이 서비스·DB 접근보다 먼저 수행되고, 리뷰 이벤트는 트랜잭션 커밋 후 발행되도록 기존 테스트를 보완했다.
- PIN 검증이 있는 등록 경로에도 요청 제한을 적용하고 제한용 메모리 저장소의 크기를 제한했다.
- MCP 주소는 서버 설정에서 받아 표시한다. 잘못된 URL·인증정보가 포함된 URL을 거부하고 설정 오류에 원문을 노출하지 않는다.
- 토큰 원문은 발급 화면 상태에만 두며 복사 피드백을 제공한다. PIN을 MCP 설정에 저장하도록 잘못 안내하던 문구를 수정했다.
- 요청 제한 시간 타이머를 정리하고, 시간 초과가 쓰기 작업의 취소를 의미하지 않음을 오류에 표시했다.
- DB 저장 오류가 토큰 해시나 원시 SQL 매개변수를 로그에 노출하지 않도록 정제했다.
- 문서 명령은 기존 모델의 생성·수정·삭제 함수를 사용한다. 삭제 시 하위 객체와 관계를 정리하고 새 객체에는 기본 배치를 생성한다.
- 사용자가 조회한 버전·동기화 순서를 확인하고, 고수준 명령의 안정적인 해시와 작업자를 비교해 재요청을 처리한다.
- 거부된 작업의 재요청과 undo·restore도 성공으로 잘못 표시하지 않는다. 생성한 동기화 입력은 기존 계약으로 검증한다.
- Caddy에서 HTTP 자동 리다이렉트를 끄고 허용 CIDR에만 upstream을 제공한다. 기존 WebSocket URL의 세션 값이 남지 않도록 proxy access log는 기록하지 않는다.

## 직접 수행한 검증

- 기존 인증 및 토큰 테스트 2개 파일, 5개 테스트 통과.
- MCP 문서·서버·토큰·보안 테스트 4개 파일, 9개 테스트 통과.
- 최종 `pnpm format:check`, `git diff --check` 통과.
- 검토용 DB를 기존 로컬 PostgreSQL에 별도로 생성하고 전체 마이그레이션을 적용했다. 실제 프로젝트 DB는 수정하지 않았다.
- 검토용 서버에서 브라우저로 사용자 등록, MCP 화면 열기, 토큰 발급, 복사 완료 표시, 닫았다 다시 열었을 때 원문 비노출, 토큰 폐기를 확인했다. 화면 콘솔 오류는 없었다.
- 실제 SDK `StreamableHTTPClientTransport`로 initialize, tools/list, 조회, 토큰 발급 응답의 `no-store`, 폐기 후 다음 요청의 401을 확인했다.
- 검토 시점 JSONL 로그 7건이 허용된 메타데이터만 포함하고 토큰 원문·Authorization·PIN·토큰 해시를 포함하지 않음을 확인했다.
- 최종 빌드에서 15개 도구 등록과 다음 복합 흐름을 실제 HTTP SDK로 검증했다.
  - 도메인, 테이블 2개, 컬럼 2개, PK, FK 관계, 메모를 한 작업으로 생성하고 진단 결과가 비어 있음을 확인했다.
  - 인증된 사용자가 작업자로 기록되고 같은 operation ID·입력의 재요청이 같은 결과를 반환했다.
  - 같은 조회 버전·순서에서 도메인을 동시에 수정하는 두 요청 중 정확히 하나만 성공하고 다른 하나는 충돌로 거부됐다.
  - 도메인 삭제가 테이블·컬럼·키·관계·메모를 함께 정리했다.
  - 삭제 복원은 새 도메인 ID로 모든 하위 객체를 복구했고 진단 결과가 비어 있었다.
- 공식 `caddy:2` 이미지를 네트워크가 차단된 임시 컨테이너에서 실행해 설정 adapter 변환을 확인했다. 443, redirect 비활성화, 허용 CIDR 분기, 기본 403, access log 폐기, `flush_interval -1`이 생성됐다.
  - 이미지 digest: `sha256:13ba145cba2f3e28fa801994876e4c086d1b95d5aa2a520a734765ffb6b12017`
  - CIDR 미지정은 parser 오류가 아니라 빈 허용 matcher가 된다. 전체 허용 기본값은 없다.
  - 이 검증은 인증서 파일 로딩이나 실제 TLS 연결 검증을 포함하지 않는다.

## 전체 검증과 정리

- 구현 에이전트의 전체 검증: workspace 타입 검사·production build, 60개 파일의 단위 테스트 297개, 격리 DB의 API·WebSocket·MCP 통합 테스트 22개 통과. 기본 단위 실행에서 제외된 DB 테스트는 격리 DB에서 별도로 실행했다.
- Vite의 기존 큰 chunk 경고는 남아 있으나 빌드는 성공했다.
- 검토용 프로젝트와 발급 토큰을 삭제·폐기한 뒤 검토 서버를 종료하고 검토 DB를 삭제했다. 브라우저 검토용 탭이 남아 있지 않음을 확인했다.
- 기존 사용자 수정 파일과 미추적 QA 파일은 커밋에 포함하지 않았다. `docs/EZERD.txt`는 변경하지 않았다.
- 서브 에이전트나 검사 도구에서 429 오류가 발생하지 않아 새 세션 포크는 실행하지 않았다.
- 실제 운영 활성화에는 사내 DNS·인증서·CIDR 설정과 다른 장치의 HTTPS/Codex 접속 확인이 필요하다. 방화벽·인증서·사용자 실제 MCP 설정은 이 작업에서 변경하지 않았다.
