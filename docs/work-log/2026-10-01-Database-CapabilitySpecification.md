## 구체화한 결정

- PostgreSQL 18, MySQL 8.4/InnoDB, SQLite 3.45 프로필을 기준으로 타입/별칭/파라미터와 native 기능을 정의했다. SQLite STRICT는 테이블별 옵션이며 일반 affinity와 구분한다.
- 타입 카탈로그·활성 정책·문서 v2·구조화된 생성/기본값·새 indexes/checks 컬렉션·DB별 UI/서버/MCP 검증 적용 위치를 명시했다.
- 프로젝트 row와 문서의 DB 설정을 일치시키고 DB 설정 변경 번호로 동시/오프라인 쓰기를 보호하도록 설계했다. 기존 metadata PATCH 대신 DB 변경 preview/change 흐름을 정했다.
- v1 읽기/업그레이드·JSON/clipboard/history 호환 및 기존 비호환 설계의 복구 정책을 기록했다. 원본 오류를 조용히 다른 DB 의미로 바꾸거나 문서를 열 수 없게 하지 않는다.
- 초안 저장 가능성과 native DB 기능 신규 사용 금지를 분리하고 오류 계약·진단 이동·전체 물리 설계 DDL 다운로드를 정했다.
- C1~C8 단계, 타입/F1/F2 활성 기준, 코드 적용 위치 및 필수 테스트 시나리오를 구체화했다. 타입·기능 표는 구현 목표이며 현재 지원 완료 목록으로 표시하지 않았다.

## 조사와 검증

- 현재 프로젝트 DB 저장, SyncService의 row lock/raw diff/baseline, MCP 최종 후보 구조 검증, 타입 옵션/기본값/serial→FK 복사, JSON v1/전역 ID/용량 제한을 읽었다.
- PG18/MySQL8.4/SQLite 공식 타입·컬럼·제약·인덱스·기본값·STRICT 자료로 지원표를 교차 확인했다. 자료 링크는 해당 규칙에 가까이 배치했다.
- 문서 간 상대 링크와 이번 diff의 공백 오류를 확인한다. 문서는 Prettier 제외 대상이다. 제품 코드가 바뀌지 않아 제품 테스트/빌드/실제 DB 실행은 이번 설계 작업에서 수행하지 않았다.
- `docs/EZERD.txt`, 기존·동시 작업의 제품 변경은 수정하거나 커밋에 포함하지 않는다.

## 구현 착수 조건

- 설계 작업 중 사용자가 `Worker 1 - Sol`의 최종 완료 후 계획 기반 구현을 지시했다.
- 대상: local 채팅 `01a0f2c6-98c0-7492-8259-2ff01242370b`. 확인 당시 진행 중 turn은 `01a0f314-cc8d-7a32-b308-145ee97c80c2`이며 도메인 필터를 개인 화면에만 적용하고 실제 설계/배치는 공유하는 후속 작업 중이다.
- 현재 완료 전이므로 제품 구현은 시작하지 않았다. 최종 결과와 Git 상태를 다시 확인한 뒤 최신 코드에 맞춰 C1부터 구현한다. 다른 채팅의 활성 변경을 이번 커밋에 섞지 않는다.
