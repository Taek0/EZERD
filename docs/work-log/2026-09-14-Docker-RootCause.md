# Docker 시작 실패와 DB 포트 충돌 근본 원인 조사

## 결론

Docker Desktop 4.83.0이 기존 Windows 런타임 소켓을 정리하지 못했을 때 Inference manager 오류를 전체 backend 시작 실패로 처리했다. 로컬 로그와 Docker 공식 수정 내역에 근거하면 잔존 소켓 처리 결함과 일치하는 사례로 판단한다. 특정 Windows 커널 결함이나 NTFS 손상이 최초 원인인지는 확정하지 못했다.

별도로 DB 포트 55432는 Windows 예약 범위에 들어 바인딩이 거부됐다. 현재 포트 15432는 사용 가능하며 DB는 정상 상태다.

## 확인한 근거와 시간 순서 (KST)

- 환경: Windows 11 Pro 25H2, 26200.9445; Docker Desktop 4.83.0, Engine 29.6.2.
- 오류 소켓 생성 시각: 2026-09-14 11:36:04. 재부팅 전 생성된 객체다.
- 18:03:54 User32 1074: 시작 메뉴에서 재시작 요청.
- 18:04:09 EventLog 6006, 18:04:11 Kernel-General 13: 종료 기록.
- 18:04:24 OS 부팅. 해당 조사 구간에는 Kernel-Power 41 및 EventLog 6008 비정상 종료 기록이 조회되지 않았다.
- 18:13:26 Docker backend 로그: dockerInference remove 실패로 backend cancelling.
- 18:13:29 Docker backend 로그: engines shutdown 및 backend crashed. Linux 엔진 파이프 부재는 이 시작 실패의 후속 증상이다.
- 18:14:49 소켓 부모 폴더를 백업 이름으로 변경하고 재시작한 뒤 엔진 응답 복구.
- 오류 소켓뿐 아니라 현재 동작 중인 새 소켓에도 fsutil reparsepoint query가 오류 1920을 반환한다. 이 명령 결과만으로 파일 손상이나 비정상 reparse tag를 판정할 수 없다.
- 부팅 시 NTFS 이벤트 98은 C: 및 D:를 정상으로 보고했다. 이 결과는 모든 저장장치 결함을 배제하는 정밀 검사가 아니다.

## 포트 충돌

- netsh의 현재 TCP 동적 범위: 49152–65535.
- 예약 범위 55390–55489가 기존 DB 포트 55432를 포함했다. 조회 시 해당 포트의 TCP listener는 없었다.
- HNS와 WinNAT 서비스는 실행 중이다. 가상 네트워크의 동적 예약과 일치하는 형태지만, 특정 서비스가 이 범위를 예약한 주체임을 증명하는 기록은 확보하지 못했다.
- Microsoft-Windows-WinNat/Oper 로그는 비활성 상태여서 예약 시각과 생성 주체를 소급 확인하지 못했다.
- 이전 복구에서 .env의 DB 포트와 연결 URL을 함께 15432로 변경했다. 동적 범위 밖이라는 점이 이번 예약 충돌 회피에 유리하지만 영구적인 포트 가용성을 보장하지는 않는다.

## 외부 근거와 재발 방지

- [Docker Desktop 공식 릴리스 노트 4.89.0](https://docs.docker.com/desktop/release-notes/#4890): 2026-08-31 Windows 수정 항목에 비정상 종료 후 남은 stuck socket 때문에 시작에 실패하는 문제 수정이 명시돼 있다. 4.90.0에도 같은 항목이 있다.
- [Docker 공식 이슈 저장소 #531](https://github.com/docker/desktop-feedback/issues/531): 사용자 보고에서 Inference/Secrets 소켓 삭제 오류 1920, 전체 엔진 시작 중단, 부모 디렉터리 이름 변경 복구가 일치한다. 이는 별도 사용자 보고이며 이 PC의 강제 종료나 커널 결함을 입증하지 않는다.
- 권장: 관련 수정이 포함된 Docker Desktop 4.89.0 이상 안정 버전으로 업데이트한 뒤 정상 종료·재시작 및 다음 Windows 재부팅 후 DB 실행을 확인한다. 이번 요청은 원인 조사이므로 업데이트나 재부팅은 수행하지 않았다.
- 현재 버전에서 폴더 이름 변경은 복구 우회책이며 결함 자체를 수정하지 않는다.
- Docker가 재부팅 과정에서 소켓 정리를 마치지 못한 정확한 이유는 기존 로그만으로 확정하지 못했다. 재발하면 종료 직전부터의 backend 로그와 Windows 파일 접근 추적이 추가로 필요하다.

## 검증과 변경 범위

- 조사 후 docker info: 29.6.2 응답; PostgreSQL healthy, 127.0.0.1:15432 유지.
- 실행 중인 서비스, 소켓, 시스템 네트워크 설정은 이번 조사에서 변경하지 않았다.
- 조사 계획·결과 문서만 커밋한다. 기존 문서 재분류 등 다른 변경은 포함하지 않는다.
