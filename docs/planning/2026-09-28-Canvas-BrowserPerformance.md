# 브라우저 자동화 기반 성능 측정 세부 계획

작성일: 2026-09-28
상태: 계획 작성. 브라우저 연결·조작, 계측 도구 구현, 실제 성능 측정은 아직 수행하지 않았다.
검토 기준: HEAD `0fd0a81`. 다국어 지원 등 별도 작업의 미커밋 변경이 존재하므로 현재 작업 트리를 확정 성능 기준선으로 사용하지 않는다.

## 범위와 기존 계획의 관계

사용자가 요청한 ‘자동화를 사용한다면 어떻게 측정할지’의 실행 설계다. [7단계 조사 절차](./2026-09-28-Canvas-PerformanceInvestigation.md)의 터미널 계측에 브라우저 시나리오를 추가한다. 이전 자동화 제외 방침의 대안이며, 이번 문서화 요청을 실제 브라우저 실행 또는 기존 사용자 데이터 변경 요청으로 해석하지 않는다. 후속 측정 작업에서 자동화 경로를 선택하면 아래 안정성 점검부터 수행한다.

목표는 에이전트가 작은 fixture부터 정해진 조작을 실행하고 앱 내부 지표를 수집해 재현 가능한 비교표를 만드는 것이다. 도구 왕복 시간이나 에이전트가 다음 행동을 결정하는 시간은 앱 성능 지표에 포함하지 않는다.

## 역할과 도구 지원 범위

| 구성 | 역할 | 보장하지 않는 것 |
| --- | --- | --- |
| 터미널 runner | 고정 데이터 생성·계산 벤치마크·통계·결과 파일 관리 | DOM·실제 입력·GPU 성능 |
| 앱 계측 어댑터 | 계산 span, 호출 수, 처리 이벤트·카메라 반영·캐시 hit/miss 기록 | 독자적인 실제 화면 표시 완료 판정 |
| 테스트 전용 제어 패널 | fixture 로드·reset·arm·finish·결과 표시 및 내보내기 | 임의 앱 내부 상태를 외부에서 직접 조작하는 통로 |
| Browser 자동화 | UI를 통한 준비·조작·완료 확인·표시된 결과 수집 | 모든 브라우저에서 동일한 입력 빈도·trace·CDP·heap 도구 |
| 선택적 성능 trace | scripting/layout/paint 및 브라우저 이벤트 진단 | 제공되지 않는 GPU 시간·메모리의 추정 대체 |

브라우저 실행 시 `browser:control-in-app-browser` 스킬과 선택된 브라우저의 전체 API 문서를 먼저 확인한다. 현재 스킬은 연결된 브라우저의 문서화된 API를 사용하도록 요구한다. 임의 CDP 연결이나 별도 Playwright 서버가 지원된다고 가정하지 않는다. 외부 라이브러리인 browser-use Python 패키지 도입은 이 계획의 전제 조건이 아니다.

초기에는 조작·관찰이 가능한지 확인하고 기능 표를 작성한다. drag/wheel 연속 입력, 결과 텍스트 읽기, 다운로드, 성능 trace는 각각 ‘지원/미지원/미확인’을 기록한다. 미지원 기능은 우회했다고 주장하지 않고 아래 대체 절차로 분리한다.

- JavaScript 평가가 가능하더라도 해당 도구가 허용하는 범위만 사용한다. 결과는 우선 화면에 노출된 요약·JSON 또는 테스트 패널의 내보내기로 수집한다. 숨겨진 전역 상태 접근이나 이벤트 주입에 의존하지 않는다.
- drag/wheel API가 없으면 해당 자동화 시나리오는 미지원으로 남기고 수동 조작과 내부 재생 실험을 구분한다.
- trace가 없으면 앱 계산 지표·DOM 수·rAF 간격까지 측정하고 layout/paint/GPU 원인 확정은 수동 프로파일링으로 남긴다.
- 다운로드 지원이 없으면 제한된 크기의 결과 JSON을 화면에 표시해 읽고 터미널에서 파일로 저장한다. 원시 결과 전체를 읽지 못하면 raw 누락 상태로 표시한다.

## 환경과 안전한 fixture

1. 기준 A·실험 B를 고정된 커밋으로 준비한다. 현재처럼 다른 작업이 진행 중이면 공유 작업 트리를 checkout·reset하지 않는다. 안정된 별도 checkout/빌드 또는 변경 완료 후 고정 커밋을 사용한다.
2. 실제 `Canvas`·카드·관계 컴포넌트를 사용하는 메모리 fixture 화면을 만든다. 합성 데이터와 가짜 저장·동기화 어댑터를 연결하며 기존 로그인 세션·운영 프로젝트는 쓰지 않는다.
3. production과 같은 최적화로 빌드한 테스트 전용 진입점에 계측·제어 패널을 포함한다. 정상 배포에는 포함하지 않는다. 기존 Vite preview가 API까지 제공한다고 가정하지 않으며 테스트 페이지는 자체 메모리 어댑터로 동작하도록 한다.
4. 로컬 loopback의 사용 가능한 포트 하나에 서버를 실행하고 PID·주소·빌드 SHA를 기록한다. 이미 사용 중인 서버를 임의 종료하지 않는다. 실행 명령과 테스트 진입 URL은 도구 구현 시 확정한다.
5. viewport 1440×900 CSS px, 앱 UI 배율 100%, locale `ko`, DPR·주사율·브라우저 버전·패널 상태를 기록한다. 언어가 텍스트 치수를 바꾸므로 영어 UI 비교는 별도 case로 분리한다.
6. 공유 파일의 개인 데이터·인증 정보는 수집하지 않는다. 오류 원인은 테스트 페이지 로그·측정 상태·자체 서버 로그 범위에서 확인한다.

## 계측 어댑터와 제어 패널 계약

다음은 새로 구현할 계약이며 현재 API가 아니다. 제어 패널 버튼은 안정적인 접근성 이름과 식별자를 제공하고, 사용 중인 locale과 무관한 시나리오 ID를 화면에 표시한다.

| 상태/기능 | 동작 |
| --- | --- |
| `reset` | fixture·카메라·선택·큐·계측 버퍼를 초기 상태로 복원한다. cache 유지/비움 조건을 별도로 선택한다. |
| `ready` | fixture 해시 확인, 폰트 준비, 초기 렌더·예정된 테스트 작업 종료 후 준비 완료를 표시한다. 제한 시간 초과는 실패다. |
| `arm` | run ID·시나리오·입력 대상을 고정하고 계측을 대기시킨다. 버튼 클릭 자체를 대상 입력으로 세지 않는다. |
| `running` | 대상 편집 영역에서 첫 유효 이벤트를 받으면 앱 내부 시계로 시작한다. 종료 조건까지 이벤트·계산 span을 수집한다. |
| `finish` | 마지막 입력 처리·예약 flush 완료를 확인하고 종료한다. 고정 시간 창 실험은 앱 내부 타이머로 종료하고 종료 이후 입력은 별도 계수한다. |
| `result` | 집계·정확성 결과·raw 크기·손실 여부를 고정하고 자동 갱신을 멈춘다. 그 후 DOM 집계·스크린샷·내보내기를 수행한다. |
| `failed` | timeout·예외·버퍼 초과·상태 불일치와 마지막 완료 동작을 기록한다. 부분 결과를 성공 표본으로 합치지 않는다. |

모든 run은 `schemaVersion`, run ID, 기준/실험 SHA, fixture ID·해시, 환경, 계측 모드, cache 조건, scenario, 입력 수, 시작·종료 상태, 지표 단위, 표본 수, 실패·미지원 항목을 포함한다.

시간은 페이지 내부의 단조 증가 시계를 기준으로 한다. 서로 다른 프로세스·클라이언트의 timestamp를 동기화 없이 빼지 않는다. span은 계산 이름·객체 ID·시작·종료를 포함하고 중첩 span을 총시간에 중복 합산하지 않는다. React 렌더 호출·commit·DOM 변경을 구분하며 commit 계측은 profiling 지원 빌드에서만 사용한다.

측정 중 패널 재렌더·console 출력·전체 DOM 스캔·스크린샷·JSON 직렬화를 하지 않는다. 메모리 버퍼는 상한을 두고 초과 시 손실 수를 기록한다. 상세 span과 단순 카운터 모드를 분리하고, 동일 동작의 계측 off/on 비교로 오버헤드를 확인한다. raw export는 측정 종료 후 수행한다.

## A단계 — 자동화 안정성 점검

과거 앱 비정상 종료 보고가 있었으므로 처음부터 대형 데이터나 반복 세션을 열지 않는다.

1. 테스트 탭 1개와 fixture 서버 1개로 시작한다. 10개 테이블·테이블당 5개 컬럼·관계 10개를 로드한다.
2. 관찰 → 카드 선택 → 짧은 드래그 → 줌 버튼 → 이름 한 번 편집 → reset을 차례로 수행한다. 매 동작의 성공과 오류를 확인한다.
3. 같은 순서를 3회 반복하고 서버·탭 응답, reset 결과, 오류 상태를 기록한다. 이 단계는 안정성 확인이며 성능 결론을 내리지 않는다.
4. 안정성 점검 통과 후 50/10/1배에서 단일 계측 run을 수행한다. 결과 JSON의 필수 필드·유효한 계산값·raw 수량을 확인한 뒤 반복 수를 늘린다.

응답 제한은 ready 30초, 개별 동작 10초, 측정 종료·내보내기 30초를 초기값으로 둔다. 환경에 맞게 변경하면 실행 전에 기록한다. crash·연결 끊김·반복 timeout이 발생하면 부하를 늘리지 않는다.

## B단계 — 시나리오별 자동화 동작

표의 좌표는 화면에 관찰된 카드와 캔버스 영역에서 계산한다. 이전 run의 화면 좌표를 그대로 재사용하지 않는다. 비편집 영역이나 대화상자가 입력을 가로채지 않는지 시작 전에 확인한다.

| ID | 준비·조작·종료 | 앱 내부 지표와 정확성 확인 |
| --- | --- | --- |
| LOAD | 새 테스트 탭에서 고정 fixture URL 열기 → ready 확인 | 앱 초기화·fixture 준비·첫 렌더 구간. 앱 시작 전 네트워크는 도구가 지원하는 경우만 별도 수집. 실제 프로젝트 네트워크 로딩으로 일반화하지 않는다. |
| PAN | zoom=1, 선택 없음 → 빈 캔버스를 300px 수평 드래그 → pointer 종료 | 이벤트·카메라 반영·치수·경로 계산 수, 카메라 이동량. 카드 좌표·문서 해시 불변. |
| ZOOM | 고정 카메라 → 같은 중심점에서 지원되는 wheel/pinch 입력 → 반대 방향 입력 | 처리 delta·배율·중심점·경로 계산 수. 버튼 zoom은 별도 ID로 두고 pinch와 같은 결과로 섞지 않는다. |
| MOVE | t000을 선택해 200px 이동 → 종료 → undo → redo | 이동·확정 시점, 관련 카드/관계 계산, 최종 문서 좌표. 화면 px는 zoom으로 문서 좌표 변환. |
| EDIT | t000의 이름/컬럼을 짧은 값→고정된 긴 한글 값으로 변경·확정 | 치수·경로·렌더 횟수와 저장 값. ‘fill로 한 번 변경’과 ‘키 입력 순차 변경’을 다른 시나리오로 둔다. |
| LIST | 목록·상세 패널을 고정 상태로 열기 → 실제 목록 영역을 일정 방향으로 스크롤 | row DOM 수·상세 계산 수, 마지막 항목 접근·선택 행 확장 높이·포커스 유지. |
| VIRTUAL | 가시 카드 위치 고정, 화면 밖 카드만 증가 → 같은 PAN 반복 | 가시/전체/마운트 수, 계산량, 팝인. 정지 후 screenshot 및 화면 밖 관계 연결 확인. |
| SYNC | 패널에서 합성 원격 변경 흐름을 예약 → MOVE 수행 → 입력 종료 뒤 큐 배출 확인 | 로컬 처리 시간·원격 backlog·반영 지연·최종 상태. 동일 객체 충돌과 다른 객체 변경을 분리. |
| EXPORT | 비중앙 카메라·축소 상태 → 테스트 PNG 내보내기 | 앱 내부 export 시간·전체 뷰 포함·크기·화면 밖 라벨. 다운로드 완료 시간과 이미지 생성 시간을 분리. |

첫 비교는 PAN·MOVE·EDIT 세 가지로 제한한다. 각 시나리오에서 1회 준비 실행 후 독립 reset 기반 5회 실행한다. 계산 전용 30회 반복은 터미널 runner에서 계속 유지한다. 모든 입력은 관찰된 UI와 지원 API로 실행한다.

연속 10초 부하·초당 60/120/240 입력 실험은 자동화 호출 속도로 만들지 않는다. 테스트 패널에서 내부 재생기를 시작해 수행하고 `mode=internal-replay`로 기록한다. Browser의 실제 입력 경로는 `mode=browser-input`으로 구분한다. 내부 재생은 렌더 파이프라인을 검사할 수 있지만 네이티브 입력 전달·hit test 전체를 검증하지 않는다.

## C단계 — 비교·확장·통계

1. 50/10/1배에서 A-B-B-A 순서로 실시한다. 기준·실험 모두 같은 계측 설정을 사용한다. 마지막 문서 상태와 입력 수를 확인해 잘못 실행된 표본을 제외하되 제외 사유·수량은 보존한다.
2. 100개·300개 순으로 늘리고 이후 컬럼 30개·관계 3배를 포함한 12종으로 확장한다. 가장 큰 fixture 실패 시 큰 크기 반복을 중단하고 마지막 성공 크기를 기록한다.
3. run별 계산 span 중앙값·p95, 계산·commit 수, 총 동작 시간, rAF 분포, DOM 수를 저장한다. 지표마다 표본 단위를 명시한다. 5개 run의 p95를 안정적인 대규모 통계로 표현하지 않는다.
4. Browser가 생성한 실제 이벤트 수·총 delta·경로가 다르면 동일 동작으로 묶지 않는다. 총비용과 이벤트/commit당 비용을 함께 보고하고 입력 차이가 큰 비교는 재실행한다.
5. 기존 잠정 목표인 대상 계산 p95 20% 개선과 다른 시나리오 10% 초과 악화 재확인을 사용한다. 실측 편차가 개선폭과 비슷하면 반복 또는 보류한다. 실제 input-to-present가 없으면 ‘입력 지연 개선’ 대신 확인한 처리 구간만 보고한다.
6. 메모리는 시간 측정과 별도 run에서 수집한다. 앱 캐시 항목 수와 데이터 byte는 수집 가능하지만 heap/GPU 메모리는 지원 도구가 있을 때만 추가한다.

## D단계 — 성능 trace와 수동 확인

trace 기능이 문서화되어 있고 사용 가능하면 작은 대표 fixture 하나에서 측정 전 시작·종료 후 저장한다. trace 자체의 오버헤드가 있으므로 해당 run은 일반 시간 비교와 분리한다. 앱 span을 브라우저 scripting/layout/paint 구간과 연결하고 계산 병목과 렌더링 병목을 구분한다.

trace 미지원 시 Browser로 DevTools를 억지로 조작하거나 임의 프로토콜을 연결하는 것을 기본 경로로 삼지 않는다. 앱 계측 결과를 먼저 확정하고 수동 trace를 별도 항목으로 남긴다. screenshot은 정지 상태의 시각 검증 자료이며 FPS나 일시적인 깜빡임 부재의 증거가 아니다. IME 조합·터치패드 감각·실제 디스플레이 지연 등 자동 입력으로 대표하기 어려운 항목도 수동 확인 범위에 둔다.

## 중단·복구·정리

- crash·브라우저 연결 해제·응답 제한 초과 시 현재 run을 `failed` 또는 `incomplete`로 기록하고 다음 대형 run을 시작하지 않는다. 마지막 완료 checkpoint를 파일에 남긴다.
- 단순 stale tab과 브라우저 연결 해제를 구분해 스킬의 문서화된 복구 절차를 따른다. 원인 확인 후 같은 최소 fixture에서 재시도는 최대 1회로 제한한다. 재발하면 브라우저 측정을 중단하고 터미널 결과와 미완료 항목을 보고한다.
- 자동화 실패를 성능 개선이나 앱 crash 원인 확정으로 해석하지 않는다. 도구 통신·서버·페이지 오류를 관찰한 근거만 기록한다.
- 각 run 결과는 종료 직후 저장해 긴 세션 crash로 모든 결과를 잃지 않게 한다. raw가 불완전하면 성공 통계에 넣지 않는다.
- 종료 시 이번 테스트가 만든 탭·서버만 정리한다. fixture 파일은 생성 manifest의 정확한 경로를 확인해 제거하며 사용자 세션·다른 서버·실제 데이터를 정리 대상으로 삼지 않는다.

## 구현 단위와 완료 조건

1. fixture·계측 어댑터·제어 패널 구현 및 터미널에서 집계·reset 정확성 검증.
2. 최소 Browser 안정성 점검 및 기능 지원표 작성.
3. PAN/MOVE/EDIT의 기준 결과 저장·schema 검증·실패 기록 검증.
4. 개선안 하나와 A/B 비교 후 관련 테스트·타입·빌드 확인.
5. 나머지 시나리오·데이터셋 확장 및 수동 확인이 필요한 부분 명시.

각 단위는 독립 커밋과 work-log를 남긴다. 폴더 정리·다국어 등 동시 변경은 측정 중 끼워 넣지 않는다. 저장 결과는 `artifacts/performance/<날짜>/<run-id>/` 후보 경로에 JSON·CSV·선택적 screenshot/trace를 두며, 기록 파일의 보존·Git 추적 정책은 구현 시 확정한다.

최종 보고에는 기준/실험 SHA, 도구 지원표, 브라우저와 내부 재생의 구분, 환경·입력·cache 조건, 원시 결과 위치, 정확성 결과, 실패·미측정 항목을 포함한다. 계측값이 정상 출력되는 것과 사용자가 체감하는 성능 개선이 검증된 것을 별도로 판정한다.
