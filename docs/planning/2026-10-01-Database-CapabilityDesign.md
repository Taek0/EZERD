# 프로젝트 DB별 타입·기능 집합 설계

> 구체화한 구현 기준: [타입·기능·모델·검증·전환 명세](2026-10-01-Database-CapabilitySpecification.md), [DB별 타입·기능 지원표](2026-10-01-Database-TypeFeatureMatrix.md). 이 문서는 방향 검토 기록이며 실제 구현 순서와 세부 기준은 후속 명세를 따른다.

## 요청과 작업 범위

- 사용자는 지원 DB별 타입과 기능을 합집합으로 구현하고 프로젝트의 선택 DB가 지원하는 집합만 사용할 수 있게 하는 구조에 대한 의견을 요청했다.
- DB별 타입/기능 정의, 프로젝트별 편집·저장·DDL 검증, DB 변경 및 기존 데이터 호환 전략을 설계한다.
- 이번 작업은 설계 검토와 문서 기록이다. 제품 코드를 구현하지 않는다.
- [기존 DDL 계획](2026-10-01-DDL-MultiDatabaseExportPlan.md)을 참고하고 타입 변환 중심의 첫 구현보다 프로젝트 DB를 설계 기준으로 삼는 구조를 우선 권고한다. 사용자의 최종 구현 승인을 의미하지 않는다.
- 기존·동시 작업의 변경과 `docs/EZERD.txt`는 수정하지 않는다.

## 권고

사용자의 방향을 권장한다. 제품이 제공하는 타입·기능 정의는 지원 DB의 합집합으로 관리하고, 프로젝트가 사용할 수 있는 집합은 선택 DB의 정책에서 얻는다. 설계 화면, 입력 검증, 서버 저장과 DDL 생성이 같은 정책을 사용하면 출력 단계의 임의 변환과 화면/서버 간 불일치를 줄일 수 있다.

개념적으로 `사용 가능한 기능 = 제품에서 구현한 기능 ∩ 선택 DB/지원 버전/모드가 허용하는 기능`이다. 단순히 타입명 목록을 필터링하는 수준보다 타입별 옵션·객체별 제약을 포함해야 한다. DB 공식 문서에 있는 기능을 카탈로그에 등록한 상태와 실제 편집·저장·DDL·실행 검증까지 구현한 상태는 구분한다.

## 공통 정의와 DB 정책

`packages/model`을 공통 정책의 소유 위치로 삼고 web/contracts/server/MCP가 재사용한다. 모델에서 계약 패키지를 역참조하지 않는다.

예상 구성:

```text
database/catalog.ts        DB별 타입 정의, 별칭, 옵션, 기능 명세
database/profiles.ts       지원 버전·모드·엔진별 사용 가능 집합
database/validation.ts     프로젝트 DB와 객체 문맥을 받는 검증
database/dialects/*.ts     DB별 SQL 출력 구현
```

- 타입 정의: DB로 구분되는 안정적인 ID, 표시명, 별칭, 길이·정밀도·scale 등 파라미터 규칙, 배열/기본값/키에 대한 허용 조건, 구현 상태를 둔다. 같은 표시명의 타입도 DB가 다르면 별개 정의로 취급한다.
- 기능 정의: 지원 여부뿐 아니라 옵션과 조건을 둔다. ENUM은 독립 타입/컬럼 값 목록, 자동 증가는 serial/identity/auto_increment/rowid 등 별도 형태로 표현하고 해당 DB가 허용하는 형태만 활성화한다.
- 프로젝트 정책: 우선 현재 `databaseKind`를 기준으로 고정 지원 프로필을 선택한다. 향후 버전·MySQL 엔진·SQLite STRICT 모드 등의 설정을 넣으면 같은 방식으로 확장한다.
- 공통 UI 컴포넌트: 테이블/컬럼/키/관계 편집기는 공유하고 타입 선택과 옵션은 정책 데이터에서 생성한다. DB마다 편집기 전체를 복제하지 않는다.
- 기능 조합: 단일 `supportsAutoIncrement: true`만으로 끝내지 않고 대상 컬럼·키·테이블을 받아 허용 여부를 판정한다.

## 데이터 모델

기존 `type.name`, `enumId`, `length`, `precision`, `scale`, `isArray`만으로 모든 DB의 기능 옵션을 표현하기는 어렵다. DB/타입 ID와 DB별 옵션을 표현하는 명시적인 구조를 설계한다. 공통 속성은 공유하고 DB 고유 옵션은 분기된 타입으로 보관한다. 모든 타입에 모든 옵션을 nullable 필드로 붙이거나 무제한 JSON 옵션으로만 보관하는 구조는 피한다.

사용자에게는 프로젝트 DB가 이미 알려져 있으므로 매 컬럼에서 DB를 다시 고르게 하지 않는다. 저장 형식에는 DB 구분 또는 프로젝트 문맥에서 안전하게 해석 가능한 타입 ID를 둔다. 자동 증가나 generated column 등 기능은 타입명 문자열에 숨기지 않고 검증 가능한 속성으로 표현한다.

기존 문서는 읽기 호환성과 명시적 변환 전략을 마련한다. 형식 변경이 필요하면 문서/전송 포맷 버전을 함께 설계한다. 특히 이미 MySQL/SQLite로 표시된 기존 프로젝트에도 PostgreSQL 방식의 타입이 들어 있을 수 있어, DB 표시만 보고 과거 타입을 새 DB의 타입으로 재해석해서는 안 된다. 읽기 시 원본을 보존하고 호환성 진단 및 복구 경로를 제공한다.

## 동일 정책의 적용 위치

| 위치 | 적용 |
| --- | --- |
| 타입 선택 | 선택 DB의 구현 완료 타입만 표시. 기존 비호환 타입은 현재 값과 진단으로 유지하여 복구 가능하게 함 |
| 속성 편집 | 해당 타입/DB에 맞는 길이·정밀도·배열·unsigned·identity 등의 옵션만 제공 |
| 키·FK·스키마·ENUM·인덱스 | DB가 허용하는 객체/옵션과 조합을 정책으로 제어 |
| 클립보드·가져오기 | 타입 의미 및 원본 DB를 확인하고 비호환 객체의 신규 반입을 조용히 허용하지 않음 |
| 저장 API·sync·MCP | 서버가 저장된 프로젝트 DB를 읽어 결과 문서를 검증. 클라이언트가 보낸 DB 종류를 권한 있는 기준으로 신뢰하지 않음 |
| DDL | 같은 DB 정책으로 전체 설계를 최종 검증한 뒤 해당 방언으로 출력 |

구조 스키마 검증과 DB 문맥 검증은 분리한다. `packages/contracts/src/relational.ts`에 현재 붙은 PostgreSQL 전용 `validatePhysicalType()`을 모든 DB 입력의 보편 규칙으로 두지 않는다. API/sync/MCP/import는 구조를 파싱한 다음 해당 프로젝트 DB 정책으로 후보 결과를 검증한다.

프로젝트 DB 변경과 설계 저장은 같은 DB 문맥/프로젝트 버전에서 처리되어야 한다. 동시 작업 중 변경된 DB의 예전 규칙으로 쓰기가 통과하지 않도록 서버 트랜잭션의 프로젝트 읽기/동시성 처리를 확인한다. 브라우저도 DB 변경을 받으면 정책을 갱신한다.

이름 미입력 같은 편집 중 초안은 기존 제품 흐름을 보존할 수 있다. 지원하지 않는 DB 기능을 새로 사용하는 것과 미완성 설계를 구분한다. 기존 비호환 데이터를 무조건 파싱 실패로 만들어 열기·고치기를 막지 않고, 신규 사용은 차단하면서 기존 문제를 수정할 수 있게 한다. DDL은 전체가 유효해야 내려받을 수 있다.

## 프로젝트 DB 변경 정책

DB 선택은 설계 의미를 결정하므로 단순 메타데이터 변경으로 취급하지 않는다.

1. 빈 프로젝트는 바로 변경 가능하다.
2. 설계가 있는 프로젝트는 대상 DB 기준의 검사 결과를 먼저 보여 준다. 이름이 같은 타입도 의미·파라미터가 동일한지 확인한다.
3. 안전한 매핑이 있는 경우 명시적 변경 계획을 만든다. 설계 변환과 DB 변경을 하나의 버전 확인/원자적 작업으로 적용한다.
4. 배열 등 매핑이 없거나 의미 손실이 있는 기능은 해결 전 변경을 차단하거나 별도 프로젝트 복사/변환 흐름으로 처리한다. 자동 삭제·암묵적 강등은 하지 않는다.

첫 구현에서는 비호환 항목이 있는 DB 변경을 차단하고 이유를 안내하는 정책이 단순하다. 모든 DB 간 자동 변환기는 내보내기 지원과 분리한다.

## ‘타입과 기능 전부’의 지원 범위

- 타입 카탈로그는 지원 버전에서 테이블 컬럼으로 사용할 수 있는 기본 타입 전체를 목표로 한다. 별칭은 동일 타입에 묶고 내부용/컬럼에 사용할 수 없는 의사 타입은 후보로 노출하지 않는다.
- PostgreSQL에는 사용자 정의 타입도 있으므로 확장 및 사용자 타입은 추가 등록 경로를 따로 설계한다. 모든 가능한 사용자 타입을 미리 열거할 수는 없다. [공식 타입 문서](https://www.postgresql.org/docs/current/datatype.html)
- MySQL 기본 타입과 타입별 옵션은 지원 버전 기준으로 분류하고 검증한다. [공식 타입 문서](https://dev.mysql.com/doc/refman/8.4/en/data-types.html)
- SQLite 일반 모드는 타입 affinity에 따라 동작하고 STRICT 모드는 허용 타입 선언이 제한된다. 일반 모드의 추천 타입/선언과 STRICT의 타입 집합을 별도 프로필로 설계한다. 세 DB의 타입 카탈로그를 같은 고정 목록 의미로 취급하지 않는다. [타입 문서](https://www.sqlite.org/datatype3.html), [STRICT 문서](https://www.sqlite.org/stricttables.html)
- 모든 기능의 합집합은 우선 ERD 설계 대상(타입·컬럼 옵션·키·FK·스키마·ENUM·인덱스·CHECK 등)의 범위를 정한다. 권한·복제·프로시저·파티션 등 DB 전체 운영 기능까지 한 번에 포함하지 않는다.
- 정의 카탈로그를 먼저 갖추고 구현 단위는 나눌 수 있다. 구현·검증 전 항목은 사용 가능 목록에 노출하지 않는다. 모든 기본 타입의 이름 등록만으로 지원 완료라고 하지 않는다.

## 수정한 작업 순서

1. 지원 버전·ERD 기능 범위와 DB별 전체 타입/옵션 명세 및 지원표 작성.
2. 공통 카탈로그·프로필·문맥 검증과 데이터 모델/기존 문서 호환 전략 구현.
3. 서버 저장·sync·MCP·가져오기·DB 변경 검사에 같은 정책 적용.
4. 프로젝트 DB를 편집기에 전달하고 타입·컬럼·키·관계·ENUM·스키마·인덱스 UI에 정책 적용.
5. 해당 DB의 설계를 출력하는 PostgreSQL/MySQL/SQLite 생성기와 공유 메뉴 연결.
6. 모든 구현된 타입/옵션/기능 조합의 회귀 및 실제 DB 실행 검증. UI와 서버가 같은 입력을 동일하게 판정하는지 확인.

각 단위는 독립 커밋하며 설계·서버·UI·DDL은 구분하되 사용 가능으로 활성화하는 시점에는 필요한 경로가 모두 갖춰져 있어야 한다. 기존 5~8개 파일/150~300줄 예상은 PostgreSQL 메뉴 연결 기준이므로 이 구조의 구현 견적으로 사용하지 않는다.
