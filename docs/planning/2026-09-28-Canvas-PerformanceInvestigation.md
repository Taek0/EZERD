## 목적과 기존 계획의 관계

[2026-09-17 성능 계획](./2026-09-17-Canvas-Performance.md)의 목표·정확성 원칙을 실행 가능한 조사 절차로 구체화한다. 기존 문서는 당시 구현 스냅샷이며, 현재 경로와 조사 순서는 이 문서를 기준으로 한다. 기존 구현 단계 0~4와 아래 조사 단계 1~7은 서로 다른 번호 체계다.

조사 순서는 기준 측정 → 카메라 계산 분리 → 단일 변경 의존성 → 계산·표시 가상화 → 입력 스케줄링 → 렌더러 비교 → 부분 로딩이다. 1~3을 우선 수행한다. 이후 단계는 앞 단계의 결과에서 해당 병목이 남아 있을 때 진행한다. 모든 기술을 적용하는 것이 완료 조건은 아니다.

## 현재 계측 대상과 준비할 도구

웹은 이미 `apps/web/src/features/*`로 정리되어 있다. 현재 `features/tables/table-geometry.ts`는 모델 패키지의 `tableCardMetrics`, `tableCardSize`를 재수출하므로 웹 래퍼만 계측해서 모델 호출을 놓치지 않도록 한다.

| --- | --- | --- |
| 카드 치수 | `packages/model/src/table-geometry.ts`와 `features/tables/TableEditor.tsx` 소비자 | 컬럼 검색·텍스트 치수·호출 중복 |

루트에 전용 성능 명령은 아직 없다. 다음은 후속 구현할 도구의 요구사항이며 지금 실행 가능한 명령이 아니다.

- 고정 fixture 생성기: 시드·크기·관계 밀도·배치·데이터 해시를 출력한다.
- 터미널 측정 runner: 현재 순수 함수와 실제 관계 입력 준비 경로를 실행하고 원시 표본 JSON 및 요약 CSV를 저장한다. 렌더 내부 로직 추출이 필요하면 기능 동등성 검증을 먼저 별도 커밋으로 한다.
- 선택적 계측 어댑터: 계산별 시간·호출 수·객체 ID·캐시 hit/miss를 수집한다. 실제 배포에서는 비활성화하고 매 호출 console 출력은 하지 않는다.
- production 기반 메모리 fixture 화면: 실제 편집 컴포넌트를 사용하되 서버 저장 대신 메모리 어댑터를 연결한다. 기존 `prepare-dense-canvas-qa.mjs`는 개발용 기능 fixture이므로 그대로 production 성능 환경으로 간주하지 않는다.
- 입력 재생기: 동일한 카메라·문서 변경 시퀀스를 계산 경로에 제공한다. 브라우저 자동화나 실제 사용자 입력 지연 측정으로 취급하지 않는다.

도구 추가 시 실행 명령·인수·출력 위치·정리 방법을 work-log에 확정한다. 타입 변환·공유 패키지 빌드는 현재 도구 체계에 맞추며, 빌드 시간을 동작 측정에 포함하지 않는다.

## 공통 실측 규칙

### 데이터와 통제 조건

- 기본 12종: 테이블 N=50·100·300, 테이블당 컬럼 C=10·30, 전체 관계 R=N·3N의 조합. FK 대상 키와 컬럼 타입 등 모델 유효성을 검사한다.
- ID는 `t000`처럼 고정하고 난수 시드는 `20260928`로 시작한다. 같은 시드라도 생성기 버전과 데이터 해시를 함께 기록한다. 생성 비용은 편집 측정에서 제외한다.
- 기본 배치는 카드의 실제 경계를 계산한 후 격자로 놓아 겹침을 방지한다. 장애물·자기참조·동일 테이블 쌍 다중 관계·긴 한글 이름은 별도 스트레스 fixture로 분리한다.
- 단일 도메인·합성 도메인 뷰·도메인 맵을 구분한다. 도메인 맵 fixture는 도메인 수 10·30·100, 관계 수 각각 1배·3배, 짧은 이름·긴 이름으로 구성하고 기본 12종과 통계를 섞지 않는다.
- 화면 기준은 브라우저 viewport 1440×900 CSS px, 앱 배율 100%, 캔버스 배율 10%·100%로 시작한다. 실제 캔버스 영역·DPR·패널 열림·화면 내 카드 수를 기록한다.
- OS, CPU/GPU, RAM, 전원 모드, 화면 주사율, 브라우저·Node 버전, 기준·실험 커밋, 빌드 종류를 기록한다. 확장 프로그램·다른 고부하 작업을 통제하고 기본 측정에서는 CPU/네트워크 throttle을 끈다.
- 테스트 대상의 데이터 변경은 매 표본 초기 fixture로 복원한다. 초기 캐시 없음과 캐시 재사용을 별도 scenario로 측정하고 어느 캐시를 초기화했는지 명시한다.

### 시간·횟수·메모리의 정의

| 지표 | 실측 방법과 한계 |
| --- | --- |
| 계산 시간 | 동기 계산 경계 전후의 단조 증가 시계 차이. 비동기 작업은 완료까지 별도 측정한다. 준비·탐색·전체 시간을 나누고 중첩 시간을 합산하지 않는다. |
| 호출 횟수 | 함수·객체 ID별 카운터. React 렌더 함수 호출, commit, DOM 변경은 다른 지표로 기록한다. |
| React 작업 | 별도 profiling 가능한 빌드에서 commit 횟수·duration을 수집한다. 개발 StrictMode의 재실행 횟수를 production 결과와 섞지 않는다. 기본 production 빌드에서 profiler 정보가 없으면 미측정으로 둔다. |
| 프레임 상태 | 수동 DevTools Performance 기록의 Frames와 긴 main-thread 작업을 확인한다. rAF 간격은 스케줄링 대리지표이며 실제 화면 표시 완료나 GPU 시간을 뜻하지 않는다. |
| 입력 지연 | 이벤트 수신→상태 반영→다음 표시 기회를 구분한다. 가능한 이벤트의 브라우저 trace를 사용한다. pointer/wheel의 실제 input-to-present를 확인할 수 없으면 핸들러 시간·다음 rAF까지만 보고한다. |
| DOM 규모 | 편집 영역의 마운트 카드·컬럼 행·관계 SVG·사이드바 행 수를 각각 센다. 전체 데이터 객체 수와 구분한다. |
| 메모리 | 안정화 후 heap snapshot을 별도 실행에서 비교한다. JS heap, 문서 직렬화 크기, 프로세스 메모리는 각각 기록하고 GPU 메모리는 도구가 제공할 때만 보고한다. snapshot·강제 GC 비용을 시간 표본에 섞지 않는다. |

터미널 계산은 5회 준비 실행 후 30회 측정으로 시작한다. 이를 독립 프로세스 3회에서 반복하며 실행별 중앙값·p95·최솟값·최댓값을 기록한다. p95는 정렬한 n개 표본의 `ceil(0.95×n)`번째 값이다. 매우 짧은 함수는 동일 작업을 K회 묶어 총시간/K와 K를 보고하되 캐시 상태와 실제 동작을 바꾸지 않는다.

화면 측정은 1회 연습 후 10초 동작 구간을 5회 기록한다. 5개 run의 p95를 안정적인 전체 모집단 p95로 표현하지 않고 각 run의 프레임 분포와 입력 수를 함께 보고한다. 사람이 수행한 경로는 동일하다고 가정하지 않는다. 시작·종료 카메라, 실제 이벤트 수, 동작 시간을 함께 저장한다.

기준 A와 실험 B는 같은 장비에서 A-B-B-A 순서로 비교하고 다음 세트는 B-A-A-B로 바꾼다. 계측 켠 실행과 끈 실행을 별도 비교해 계측 오버헤드를 기록한다. DevTools tracing도 진단용·가벼운 계측용 실행을 분리한다. 시간 목표는 기존 계획의 잠정값인 대상 p95 20% 개선, 다른 시나리오 10% 초과 악화 시 재확인을 사용한다. 반복 편차가 개선폭과 비슷하면 결론을 보류한다.

60Hz의 16.7ms는 프레임 예산 참고값이다. 60Hz와 120Hz 결과를 같은 임계값으로 합치지 않는다. 긴 작업 비율은 `(프레임 예산 초과 표본 수)/(전체 표본 수)`로 계산하되, rAF 기반이면 ‘rAF 지연 비율’이라고 표시한다.

## 1단계 — 기준 성능 측정

**질문:** 크기·관계 밀도 증가에 따라 어느 동작의 어느 구간이 느려지는가?

1. 기본 fixture 12종의 유효성·해시를 확인한다. 50/10/1배를 가장 작은 대조군으로 사용한다.
2. 처음 뷰 생성, 전체 카드 치수 계산, 관계 입력 준비, 경로 계산, 도메인 배치를 각각 측정한다. 계산 없는 빈 루프 비용도 확인하되 임의로 결과에서 빼지 않는다.
3. 수동 화면에서 로딩 완료 후 팬, 줌, 카드 이동, 컬럼 수정, 사이드바 스크롤을 한 번에 하나씩 기록한다. fixture 설치·폰트 준비·첫 paint·조작 가능 시점은 서로 다른 경계로 남긴다.
4. 전체 CPU 시간, 계산별 시간·호출 수, DOM 수, 프레임 상태를 나란히 놓는다. 무관한 작업을 제거한 진단 실험은 원인 확인용으로만 사용하고 제품 성능 수치로 보고하지 않는다.

**판정·산출물:** 데이터셋×동작 기준표와 비용 상위 3개 구간, 미측정 항목을 남긴다. Node 계산 결과만 있으면 화면 병목 판정은 보류한다. 300개에서 실패·중단하면 마지막 성공 크기·중단 조건을 기록하고 0ms로 채우지 않는다.

## 2단계 — 팬·줌과 문서 계산 분리

**질문:** 문서 내용이 같아도 카메라 변경이 카드 치수·관계 경로 계산을 유발하는가?

1. warm 상태에서 고정 뷰의 카메라만 600번 변경한다. 팬은 x를 0→1000→0으로 이동하고 y·zoom은 고정한다. 줌은 중심점을 고정해 1→0.1→1로 변경한다. 각 시퀀스는 별도 실행한다.
2. 카메라 반영 수, `tableCardMetrics`·관계 준비·`relationGeometry`·`layoutDomainRelations` 호출 수와 시간을 센다. 단위 재생은 실제 60fps 실행이 아니라 계산 이벤트 600회의 비용이다.
3. 수동 10초 팬·줌으로 React commit과 main-thread layout/paint 비용을 확인한다. 이벤트 수가 다른 run은 총시간뿐 아니라 이벤트·commit당 비용도 비교한다.
4. 실험 B에서는 문서 좌표의 계산 결과와 카메라 transform을 분리한다. 뷰 전환·문서 변경·가시 대상 선정은 각각 다른 무효화 조건으로 둔다.

**판정·산출물:** 변경 원인→실행 계산 표. 문서와 경계가 고정된 warm 카메라 조작에서 문서 좌표 카드 치수·관계 경로의 재계산 0회를 목표로 한다. 배율 의존 표시 계산은 따로 센다. 포인터 좌표 변환·줌 중심·PNG·관계선 정합성을 확인한 뒤 다음 단계로 진행한다.

## 3단계 — 단일 편집의 의존성과 캐시

**질문:** 어느 데이터가 바뀔 때 어떤 계산을 다시 해야 정확한가?

1. `t000`의 컬럼 이름을 같은 폭 이름과 긴 이름으로 각각 변경한다. 타입·설명·enum·표시 옵션 변경, 카드 이동, 선택만 변경도 별도 case로 둔다.
2. 수정 전후 카드 크기·관계 경로·라벨 결과와 객체별 계산·렌더 횟수를 수집한다. 움직인 카드가 관계 양 끝점인 case와 무관한 관계의 장애물인 case를 구분한다.
3. 캐시 없는 전체 재계산 결과를 정확성 기준으로 둔다. ID 조회, 테이블별 컬럼·키, 카드 치수, 관계 입력 캐시를 한 종류씩 추가해 비교한다. 문서 전체 객체의 identity만 의존성으로 쓰는 캐시가 매번 무효화되는지 확인한다.
4. 관계 경로 비교는 우선 기존 알고리즘과 동일 출력을 요구한다. 알고리즘도 바꿔 경로가 달라진다면 충돌·끝점·수동 경로 보존을 별도 검증하는 후속 실험으로 분리한다.
5. 편집→undo→redo, 원격 변경, 삭제·복원, 뷰 전환을 수행해 오래된 캐시를 검사한다. 100회 반복 후 동일 문서 상태로 돌아왔을 때 캐시 항목 수·보유 메모리 추세도 비교한다.

**판정·산출물:** 캐시별 입력·무효화·해제 조건 표와 전체 재계산 동등성 결과. 연결 관계만 갱신하는 식으로 장애물 영향을 누락하면 실패다. 의존 범위를 좁힐 근거가 없으면 정확한 전체 무효화를 유지한다. 단순 처리량 개선뿐 아니라 메모리 증가도 기록한다.

## 4단계 — 표시와 상세 계산 가상화

**질문:** 전체 객체 수가 증가해도 화면에 필요한 상세 계산량을 제한할 수 있는가?

1. 카메라와 화면 내 20개 카드 위치를 고정하고 화면 밖 카드만 추가해 총 50→100→300개로 늘린다. 기본 fixture와 별도의 비교 fixture임을 표시한다.
2. 전체 뷰의 경계·연결 ID를 구하는 비용과 가시 카드의 컬럼·컨트롤을 만드는 비용을 나눠 측정한다. 화면 밖 상세 계산 수, 카드·행 DOM 수, 메모리를 기록한다.
3. A=현재 방식, B=DOM만 생략, C=DOM과 상세 계산 생략을 비교한다. 경계 계산을 매번 전체 수행한다면 남은 선형 비용으로 공개한다. 공간 인덱스는 선형 검색 자체가 병목일 때 별도 실험한다.
4. 여유 영역은 0·200·400 CSS px를 후보로 비교한다. 문서 좌표로 변환할 때 zoom을 반영하고, 빠른 팬 중 팝인·마운트 변동과 비용을 기록한다. 편집 중 카드 유지 정책을 포함한다.
5. 사이드바는 ID·순서 생성과 행 상세 정보를 분리한다. 현재 선택 행 아래 펼쳐지는 컬럼 상세의 가변 높이, 검색·키보드 이동·스크롤 위치 보존을 확인한다.
6. 낮은 배율 간소화는 가상화와 별도 실험으로 한다. 전환 경계 후보를 명시하고 반복 줌 시 깜빡임·크기 불변·편집 진입을 검증한다.

**판정·산출물:** 전체 수/가시 수 대비 계산·DOM 증가 곡선, 여유 영역 결정표. 관계선 `visibleNodeIds`는 전체 의미상 뷰 대상으로 유지한다. 양 끝 카드가 화면 밖이어도 선이 화면을 통과하는 경우와 화면 밖 장애물을 확인한다. 현재 PNG는 DOM 복제 방식이므로 전체 상세 내보내기 경로를 먼저 준비하고 시각 결과를 비교해야 채택할 수 있다.

## 5단계 — 입력·동기화 작업 스케줄링

**질문:** 입력 폭주나 원격 변경이 로컬 조작을 얼마나 지연시키는가?

1. 메모리 입력 시퀀스로 10초 동안 초당 60·120·240개 입력을 각각 제공한다. 이는 실장치 재현이 아닌 부하 실험이다. 실제 rAF 주기·처리 이벤트 수·최대 대기 길이를 기록한다.
2. 같은 로컬 드래그에 유효한 원격 변경을 초당 0·10·50개 겹친다. 원격 fixture의 객체·순서·버전을 고정하고 실제 서버 지연과 분리한다.
3. 수신→큐 진입→문서 적용→React commit의 시점을 같은 시계로 기록한다. 로컬 입력 핸들러 시간, 반영 횟수, 지연 프레임, 원격 backlog와 반영 지연을 각각 비교한다.
4. 먼저 입력 병합만 실험한다. pointer 절대 좌표는 마지막 값을 사용하고 wheel delta는 누적하거나 이벤트 순서대로 카메라에 적용해 총 이동을 보존한다. 다음 실험에서만 비긴급 표시 작업을 나눈다.
5. pointerup/cancel, blur, 뷰 전환, 컴포넌트 해제, 백그라운드 탭 전환을 검증한다. 종료 시 마지막 입력을 확정하고 예약된 callback을 정리한다. 원격 데이터 순서나 저장 의미를 변경하지 않는다.

**판정·산출물:** 큐 타임라인과 마지막 상태 동등성 결과. 이동 중 경로별 반영은 프레임당 최대 1회, 종료 flush는 별도 허용·집계한다. 로컬 지연이 줄어도 원격 변경이 계속 쌓이면 실패다. 원격 반영 지연의 허용치는 기준 측정 후 실험 전에 확정한다. UI 표시 병합을 원격 변경 폐기로 구현하지 않는다.

## 6단계 — 렌더링 방식 비교

**진입 조건:** 앞 단계 이후에도 수동 trace에서 DOM layout/paint 또는 SVG 렌더링 비용이 주요 병목으로 남는다. 단순 계산 병목이면 renderer 실험을 보류한다.

1. 동일한 사전 계산 경로·카드·라벨 데이터로 SVG 관계선과 Canvas 2D 관계선을 비교한다. 초기에는 카드·편집 UI는 그대로 유지하고 renderer 하나만 바꾼다.
2. 전체 갱신과 부분 갱신, 정지·팬·줌·단일 관계 편집을 비교한다. 폰트·DPR·선 굵기·품질·뷰포트·관계 수를 맞추고 시작 비용·steady-state·메모리를 분리한다.
3. main-thread scripting/layout/paint, 프레임 분포, hit test 비용을 기록한다. GPU가 병목이라는 결론은 GPU 관련 근거가 있을 때만 내리고 paint 시간만으로 단정하지 않는다.
4. 선택·끝점 조작·텍스트·한글 입력·포커스·접근성·PNG를 체크한다. 카드를 그래픽으로 바꾸는 후속 실험은 HTML 입력 overlay와 좌표 동기화 비용까지 포함한다.
5. WebGL/WebGPU 또는 Worker/Wasm은 별도 후보로 둔다. Worker는 데이터 전송·복사·오래된 응답 취소 비용, Wasm은 경계 호출·메모리 비용을 포함한다. 후보 구현에 따라 필요한 공식 API 문서를 다시 확인한다.

**판정·산출물:** 현행/후보의 성능·정확성·구현 및 유지 비용 비교표. 빠르게 그리지만 편집·내보내기 기능이 빠진 데모를 대체 구현으로 채택하지 않는다. 차이가 작거나 느린 기기에서 악화되면 현행 유지로 결론을 낼 수 있다.

## 7단계 — 부분 로딩과 메모리

**진입 조건:** 최초 조작 가능 시간이나 메모리 문제가 남고, 데이터 전송·파싱·초기 파생 계산이 그 원인이라는 근거가 있다.

1. 동일한 작은 현재 도메인을 유지하면서 나머지 도메인 수만 늘린 fixture를 만든다. 전체/현재 도메인 객체 수·직렬화 byte·참조 수를 기록한다.
2. 수동 Network 기록에서 요청 시작·전송 완료를 구분하고, 파싱·모델 초기화·파생 계산·첫 화면·조작 가능 시점은 앱 계측으로 별도 기록한다. HTTP 캐시 비움과 앱 파생 캐시 비움은 서로 다른 조건이다.
3. A=전체 로딩, B=전체 전송 후 선택 도메인만 파생 계산, C=필요 데이터만 전송의 실험을 순서대로 진행한다. B를 네트워크 절감으로 보고하지 않는다.
4. 먼저 메모리 어댑터에서 실험하고, C는 서버 API·동기화 계약 설계 후 격리 환경에서만 구현한다. 도메인 간 FK·enum·키·참조 테이블의 의존성 확장으로 실제 얼마나 더 불러오는지 측정한다.
5. 도메인 20회 왕복 후 메모리 추세, 다음 뷰 대기시간, 중복 전송을 확인한다. 미로딩 객체 수정·삭제·원격 변경·undo·검색·전체 JSON/DDL/PNG를 어떻게 처리할지 명시한다.

**판정·산출물:** 단계별 로딩 시간·전송량·보유 객체·메모리 표와 의존성/일관성 설계. 전체 문서가 필요한 연산의 추가 로딩 비용을 숨기지 않는다. 최초 로딩만 빨라지고 편집 정합성이 깨지면 채택하지 않는다.

## 결과 기록·실행 순서

원시 산출물은 향후 `artifacts/performance/<날짜>/<실험ID>/`에 저장하되 추적 여부·보존 정책을 구현 시 결정한다. 개인 데이터 대신 합성 fixture를 사용하고 요약은 `docs/work-log/YYYY-MM-DD-Canvas-PerformanceInvestigation.md`에 남긴다.

```text
실험 ID / 단계 / 가설:
기준 커밋 / 실험 커밋 / 계측 코드 버전:
환경 / fixture ID·해시 / cache 상태 / 빌드 종류:
실행 명령 또는 수동 동작 / 표본 수 / 원시 결과 경로:
지표 | 단위 | 기준값 | 실험값 | 변화율 | 실행 간 편차
정확성 검증 / 메모리 변화 / 계측 오버헤드:
미측정 항목 / 실패·중단 조건:
결정: 채택 / 추가 측정 / 보류 / 철회
다음 단계와 근거:
```

첫 실행 단위는 fixture·runner 준비와 기준 측정이다. 계측과 정확성 확인을 마친 뒤 2단계의 카메라 계산 분리 하나만 실험한다. 단계마다 계획상 잠정 목표를 재확인하고 독립 커밋 및 결과 기록을 남긴다. 문서·도구 추가와 제품 최적화는 분리한다. 최적화 후 관련 단위 테스트·타입·빌드를 수행하며 전체 확인 시 `pnpm check`를 사용한다. 브라우저 자동화는 사용하지 않고 수동 확인이 남으면 완료로 표시하지 않는다.
