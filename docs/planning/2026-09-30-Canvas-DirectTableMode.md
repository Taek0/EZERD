# 캔버스에서 테이블을 직접 구성하는 모드 검토

## 검토 목적

도메인을 먼저 만들지 않고 캔버스에서 테이블과 관계를 작성하는 흐름을 추가할 방향을 검토한다. 이번 작업의 범위는 기존 구조 분석과 설계 제안이며 기능 구현은 포함하지 않는다.

## 검토 계획

1. 도메인 소속, 테이블 생성, 뷰와 배치, 프로젝트 초기 진입 흐름을 확인한다.
2. 기본 도메인을 내부에서 사용하는 방식과 도메인 소속을 선택 사항으로 만드는 방식을 비교한다.
3. 기존 도메인 설계와 직접 테이블 설계의 전환, 공유 데이터와 개인 뷰의 경계, 단계별 구현 및 검증 범위를 정리한다.
4. 후속 검토로 전체 캔버스의 테이블별 색상 지정과 도메인 색상의 우선순위를 정리한다.

## 작업 경계

- 기존 캔버스 및 테이블 클립보드 작업의 미커밋 변경을 수정하거나 커밋에 포함하지 않는다.
- `docs/EZERD.txt`는 수정하지 않는다.
- 조사 결과에 따라 아래에 권장 방향과 구현 순서를 추가한다.

## 현재 구조에서 확인한 제약

- `packages/model/src/document.ts`의 `Table.domainId`와 `packages/contracts/src/relational.ts`의 테이블 계약은 도메인 ID를 필수로 요구한다.
- `addTable`은 소유 도메인의 존재를 확인하고 그 도메인 화면에 원본 배치를 만든다. `diagnoseDocument`도 소속 도메인과 원본 배치를 요구한다.
- `Canvas.tsx`는 최초 화면을 `overview`로 열고, 도메인 맵과 함께 보기에서 테이블 생성을 막는다. 일반 테이블 화면은 `table.domainId === viewId`를 기준으로 표시한다.
- `CombinedView`는 도메인 ID 목록으로 구성되며 `personal.ts`와 `sync.ts`에서 개인 상태로 분리된다. 공동 편집의 기본 화면을 기존 함께 보기로 만들면 배치·메모·관계선의 저장 의미가 달라진다.
- `postgres.ts`의 DDL 진단도 소유 도메인을 요구한다. MCP 테이블 생성·뷰 조회, 가져오기, 개인 상태 정리에도 도메인 또는 기존 뷰 종류를 가정한 부분이 있다.
- 현재 진행 중인 테이블 클립보드 작업도 소속 도메인 및 도메인 화면 배치를 사용한다. 구현 시 해당 작업과 통합해야 한다.
- 설계 문서는 프로젝트 행의 JSON 문서로 저장된다. 도메인 소속을 선택 사항으로 만드는 일은 우선 문서 모델·계약·검증의 변경이며, 테이블별 관계형 DB 컬럼의 nullable 변경으로 접근할 작업은 아니다.

## 권장 방향

테이블은 프로젝트에 속하고 도메인은 나중에 붙일 수 있는 업무 분류로 정의한다. 사용자에게는 같은 프로젝트의 `테이블 캔버스`와 `도메인 맵`을 제공한다. 직접 구성과 도메인 설계 사이의 이동은 동일한 테이블을 다른 화면에서 보는 동작으로 만든다.

이 문서는 설계 제안이다. 새 프로젝트의 기본 진입 화면 변경과 문서 버전 정책은 실제 구현 범위 확정 시 결정한다.

### 사용자 흐름

1. 프로젝트 생성 후 `테이블로 시작` 또는 `도메인으로 시작`을 선택할 수 있다. 빠른 시작을 우선한다면 테이블 캔버스를 기본값으로 제안한다.
2. 테이블로 시작하면 빈 캔버스에서 바로 테이블·컬럼·PK/FK·관계를 작성한다. 도메인 생성이나 선택은 요구하지 않는다.
3. 상단의 `테이블 캔버스 / 도메인 맵`으로 이동한다. 기존 논리·물리 보기 선택과 별개의 축이다.
4. 필요해지면 테이블 속성 또는 다중 선택 작업에서 도메인을 지정한다. 도메인을 해제해도 테이블과 관계는 유지한다.
5. 전체 테이블 캔버스에는 소속과 무관하게 모든 테이블을 표시한다. 소속을 바꾸어도 전체 캔버스의 위치는 유지한다.
6. 도메인 화면에는 소속 테이블과 기존 외부 참조 흐름을 유지한다. 미소속 테이블은 전체 캔버스에서 찾을 수 있다.

도메인을 먼저 생성한 뒤 그 화면에서 테이블을 생성하는 기존 흐름도 유지한다. 도메인 화면에서 만든 테이블은 해당 도메인에 자동 소속시키고 전체 캔버스에도 동일한 테이블 ID로 배치한다. 두 시작 흐름은 같은 프로젝트 안에서 함께 사용할 수 있다.

### 테이블별 색상 지정

- 전체 캔버스에서 테이블을 선택하고 속성 패널 또는 컨텍스트 메뉴의 `테이블 색상`으로 지정한다. 팔레트·HEX 입력·`자동 색상으로 되돌리기`를 제공하며 기존 도메인 색상 선택 UI를 공용으로 추출해 재사용한다.
- 테이블 색상은 `Table.color?: string`처럼 테이블 자체의 선택 속성으로 저장하는 방향을 제안한다. 화면별 위치와 구분하고, 모든 화면과 협업자에게 동일하게 적용한다. 특정 사용자의 개인 표시 색상은 첫 범위에 포함하지 않는다.
- 표시 우선순위는 `테이블 지정 색상 → 소속 도메인 색상 → 기본 중립 색상`이다. 색상 필드를 생략한 기존 테이블은 도메인 색상을 그대로 따른다. MCP patch의 필드 생략은 유지, `null`은 지정 색상 제거로 정의한다.
- 도메인을 지정·변경·해제해도 직접 지정한 테이블 색상은 유지한다. 자동 색상의 테이블만 소속에 따라 표시 색상이 바뀐다. 화면 이동도 지정 색상을 바꾸지 않는다.
- 현재 테이블 카드는 도메인 색상을 헤더 배경에 사용한다. 테이블 색상과 도메인 소속 표시를 분리하고 테이블 색상은 헤더의 강조 띠 또는 옅은 배경에 적용하는 방향을 제안한다. 도메인 소속은 이름·배지로 계속 확인할 수 있게 한다.
- 본문과 컬럼 텍스트의 가독성 및 기존 선택·오류 표시를 유지한다. 임의 색상을 카드 전체에 진하게 채우는 방식은 첫 구현의 기본 표현으로 삼지 않는다.
- 테이블 색상은 공유 설계 상태로 동기화하고 디자인 편집 권한을 적용한다. 값은 기존 도메인과 같이 `#RRGGBB`로 검증하며 DDL 생성에는 영향을 주지 않는다.
- 첫 범위에는 단일 테이블 색상 지정·초기화를 포함한다. 여러 테이블을 같은 색으로 바꾸는 기능은 기존 다중 선택 연산과 연결해 후속으로 추가할 수 있다.
- 저장·재접속·undo·MCP·JSON 내보내기/가져오기·복사/붙여넣기가 직접 지정 색상을 보존하는지 확인한다. PNG 출력은 카드의 최종 표시 색상이 반영되는지 검증한다.

### 데이터와 배치

- 도메인 미지정을 `domainId: null`로 표현하는 방안을 제안한다. 기존 문자열 값도 계속 허용한다. MCP 부분 수정에서는 필드 생략은 유지, `null`은 소속 해제로 구분한다.
- `overview`는 도메인 맵으로 유지하고, 전체 테이블 캔버스는 별도의 예약 뷰 ID(예: `tables`)와 명시적인 뷰 종류를 사용한다. 객체·개인 뷰의 ID 충돌도 계약과 서버에서 막는다.
- 테이블 생성과 화면 배치를 분리한다. 전체 캔버스의 기본 배치와 소속 도메인의 배치를 각각 관리하며, 도메인 지정·해제는 같은 테이블 ID의 배치를 추가·정리하는 작업으로 처리한다.
- 새 기본 배치 정책은 전체 캔버스에 테이블당 하나의 배치를 보장하고, 도메인 소속 테이블에는 도메인 원본 배치도 보장하는 방향으로 정한다. 이를 기존 문서와 동시에 적용하려면 로드 시 정규화 또는 버전 이관이 필요하다.
- 기존 테이블·컬럼·키·관계 ID는 소속 변경과 화면 이동 과정에서 유지한다. 도메인 관계는 테이블 관계와 구분하며 FK를 도메인 관계로 자동 변환하지 않는다.
- 전체 캔버스의 테이블 위치·메모·관계선 경로는 공유 설계 상태로 저장하고, 사용자별 확대·이동·최근 화면은 개인 상태로 저장한다. 기존 개인 함께 보기는 별도 흐름을 유지한다.
- 프로젝트 전체에 강제되는 모드 플래그보다 사용자별 시작 화면 선택을 우선한다. 협업자가 화면을 바꿔도 다른 사용자를 강제로 이동시키지 않는다.
- 도메인 삭제와 소속 해제를 구분한다. 기존 삭제 정책을 먼저 확인하고, 소속을 해제하는 동작이 테이블·컬럼·관계를 연쇄 삭제하지 않도록 별도 연산을 제공한다.
- 물리 테이블 이름 중복은 기존대로 DB 스키마와 테이블명 기준으로 검증한다. 도메인 이동을 DB 스키마 변경으로 취급하지 않는다.

### 대안 비교

| 접근 | 장점 | 비용·한계 | 판단 |
| --- | --- | --- | --- |
| 기본 도메인을 자동 생성하고 곧바로 그 캔버스로 진입 | 기존 모델과 DDL 검증을 대부분 유지하며 빠른 시작을 구현할 수 있다 | 실제 데이터는 계속 도메인 소속이다. 도메인 맵·속성·MCP·내보내기에서 숨김 규칙과 전환 정책이 필요하다 | 일정이 우선인 임시 MVP 대안 |
| 도메인 소속 선택화와 전체 테이블 캔버스 | 직접 작성과 나중 분류가 같은 프로젝트 안에서 자연스럽게 연결된다 | 모델·검증·공유 배치·MCP·파일 호환성을 함께 수정해야 한다 | 정식 기능으로 권장 |

두 방식을 연속 단계로 무조건 구현하지 않는다. 자동 기본 도메인 방식은 임시 정책을 후속 이관해야 하므로 일정상 필요한 경우에만 선택한다.

## 구현 순서와 커밋 단위

1. **모델·계약·호환 정책**: 도메인 선택화, 예약 뷰 종류, 생성과 배치 연산, 진단 규칙을 정의한다. 기존 문서에서 전체 배치를 만드는 규칙과 새 파일 버전의 수용·거부 정책을 함께 정한다. 지원하지 않는 구버전 클라이언트가 새 문서를 덮어쓰지 않도록 호환 경계를 정한다.
2. **서버 저장·동기화·외부 인터페이스**: 공유/개인 상태 분리, 개인 viewport 정리, 예약 ID와 삭제 복원, 권한·충돌·undo, MCP 조회·생성, 프로젝트 파일 입출력, DDL 진단을 대응한다. 기존 클라이언트와 동시에 배포할 수 있는 범위를 확인한다.
3. **전체 캔버스 UI**: 기존 테이블 카드와 편집기·관계 도구를 재사용한다. 진입 화면, 경로 표시, 빈 화면, 생성 버튼, 검색·자동 배치·내보내기를 새 뷰 종류에 맞게 연결한다. `viewId === 'overview'` 조건을 단순히 반전하기보다 화면별 기능 지원을 명시한다.
4. **나중 분류와 통합 QA**: 도메인 지정·해제와 여러 테이블 일괄 분류를 제공한다. 기존 도메인 화면·개인 함께 보기·진행 중인 복사/붙여넣기를 통합 검증한다.

각 단위는 문서와 필요한 검증을 포함해 독립적으로 커밋한다. 정식 기능을 사용자에게 노출하기 전에는 도메인 없는 모델의 저장·동기화·DDL·파일 이동까지 완료한다.

## 완료 기준

- 도메인이 0개인 프로젝트에서 테이블 2개와 FK 관계를 만들고 저장·재접속·DDL 내보내기까지 성공한다.
- 같은 테이블이 전체 캔버스와 도메인 화면에서 동일한 모델을 편집한다. 두 화면의 위치·관계선 경로는 각각 유지한다.
- 도메인 지정·변경·해제 후 테이블·컬럼·키·관계 ID와 전체 캔버스 위치가 유지된다.
- 두 사용자의 공동 편집과 viewer 읽기 전용, 기존 개인 함께 보기의 배치 권한이 정상 동작한다.
- 기존 프로젝트 로드와 새 파일 왕복 가져오기, MCP 조회·생성, 삭제 복원·undo를 검증한다.
- 전체/도메인 캔버스 사이의 복사·붙여넣기, 자동 배치, 검색, PNG 출력이 정상 동작한다.
- 테이블 지정 색상·도메인 상속·중립 색상의 우선순위가 모든 테이블 화면에서 같고, 지정 색상 초기화와 소속 변경 후에도 규칙이 유지된다.
- 테이블별 색상이 공유 저장·파일 이동·복사·PNG 출력에 반영되며 읽기 전용 사용자는 변경할 수 없다.

## 첫 구현 범위 제안

전체 테이블 캔버스 하나, 도메인 없는 테이블 생성, 기존 컬럼·키·관계 편집 재사용, 저장·협업·DDL·파일 이동, 단일 테이블의 도메인 지정·해제와 색상 지정·초기화까지를 첫 기능 범위로 잡는다. 영역 박스, 자동 도메인 추론, 임의 테이블 묶음 뷰와 고급 분류 필터는 후속으로 남긴다.
