# EZERD 데이터 모델 초안

## 현재 구현과 아래 제안의 관계

현재 저장 형식은 `schemaVersion: 1`이며 도메인·업무 관계·자유 텍스트·화면 배치와 선택적인 테이블·컬럼·키·테이블 관계 배열을 포함한다. 코드 원본은 packages/model/src/document.ts, 런타임 계약은 packages/contracts/src/workspace.ts다. 테이블·컬럼·키·관계의 논리/물리 독립 편집은 구현했다. 아래 고급 타입 사전·자동 추천·실시간 편집 항목은 후속 제안이며 실제 타입 필드는 코드 계약을 기준으로 한다. 구현 상태와 저장 검증은 [구현 진행 기록](../work-log/IMPLEMENTATION_PROGRESS.md)에 정리한다.

## 결정된 방향

논리·물리는 하나의 모델로 관리하되 각자의 특성을 독립적으로 적용한다.

- 도메인, 테이블, 컬럼, 관계의 ID는 보기 전환과 무관하게 유지한다.
- 동일 객체에 공통 정보와 논리·물리 정보를 나누어 저장한다.
- 두 모델을 복제하거나 별도의 동기화 대상으로 만들지 않는다.
- 도메인 간 업무 관계는 테이블 관계와 독립적이며, 테이블 없이도 정의할 수 있다.

아래 필드와 자료형은 이 결정을 구체화한 제안이다. 앱의 저장소, 프레임워크, 실시간 협업 라이브러리를 확정하거나 구현한 문서는 아니다.

## 객체 구성

| 구분 | 테이블 예시 | 컬럼 예시 |
| --- | --- | --- |
| 공통 정보 | ID, 소유 도메인 ID, 적용 범위 | ID, 소유 테이블 ID, 적용 범위 |
| 논리 특성 | 논리명, 업무 정의, 업무 규칙 | 논리명, 업무 정의, 논리 타입, 업무상 필수 여부 |
| 물리 특성 | 물리명, PostgreSQL 스키마, DB 설명 | 물리명, DB 타입, NULL 허용, 기본값, DB 설명 |
| 확장 속성 | 팀별 검토 정보 등 | 개인정보 분류 등 |

- 논리 타입은 '식별자', '금액', '이메일 주소' 등의 의미를 표현한다.
- 물리 타입은 uuid, numeric(12, 2), varchar(254) 등 구현을 표현한다.
- 논리 타입과 물리 타입의 연결은 추천 또는 명시적 적용 규칙으로 구현할 수 있지만, 이름·타입 변경만으로 상대쪽 값을 자동 덮어쓰지 않는다.
- 업무상 필수 여부와 DB의 NULL 허용 여부는 별도 값이다. 업무 단계에 따라 나중에 채워지는 필수 정보처럼 서로 다른 값이 필요한 경우를 허용한다.
- PK와 UNIQUE는 별도 키 객체와 순서가 있는 컬럼 ID 목록으로 정의한다. 복합 키를 지원하기 위해 컬럼의 체크박스만을 저장 원본으로 사용하지 않는다.

## 적용 범위와 보기 모드

적용 범위는 객체의 설계 데이터이며, 보기 모드는 사용자별 화면 상태다.

| 객체 적용 범위 | 논리 보기 | 물리 보기 | 함께 보기 | DDL 후보 |
| --- | --- | --- | --- | --- |
| both | 표시 | 표시 | 양쪽 특성 표시 | 포함 |
| logical | 표시 | 숨김 | 논리 전용 표시 | 제외 |
| physical | 숨김 | 표시 | 물리 전용 표시 | 포함 |

- DDL 후보라도 이름·타입·참조 등이 유효하지 않으면 내보내기 검증을 통과해야 한다.
- 부모 테이블이 해당 보기에서 제외되면 그 컬럼도 표시하지 않는다.
- 컬럼의 적용 범위는 소유 테이블의 범위를 넘어설 수 없다. 예를 들어 논리 전용 테이블 아래 물리 전용 컬럼은 유효한 구성으로 인정하지 않는다.
- 적용 범위를 바꿀 때 관련 컬럼·키·관계에 미치는 영향을 검토한다. 기존 논리·물리 값을 조용히 삭제하지 않는다.
- 모델링 중의 미완성 상태는 저장할 수 있다. 모순된 적용 범위나 참조는 진단으로 표시하고 유효한 DDL 내보내기와 구분한다.
- 각 보기는 동일한 테이블·컬럼 원본을 사용한다. 별도 레이아웃을 제공하더라도 좌표만 분리한다.

## 컬럼 예시

다음 객체는 주문의 결제 금액을 나타낸다. 논리적으로는 금액 의미와 업무 규칙을 설명하고, 물리적으로는 실제 저장 타입과 제약을 설정한다.

```json
{
  "id": "column-order-total",
  "tableId": "table-order",
  "scope": "both",
  "logical": {
    "name": "결제 금액",
    "definition": "할인 적용 후 고객이 결제할 금액",
    "semanticType": "금액",
    "required": true
  },
  "physical": {
    "name": "total_amount",
    "type": {
      "kind": "builtin",
      "name": "numeric",
      "parameters": { "precision": 12, "scale": 2 },
      "isArray": false
    },
    "nullable": false,
    "defaultExpression": null,
    "comment": "할인 적용 후 결제 금액"
  },
  "customProperties": {
    "common": { "검토 상태": "검토 중" },
    "logical": { "금액 단위": "KRW" },
    "physical": {}
  }
}
```

예시 ID는 설명용이며 실제 생성 방식은 별도로 결정한다. 이 JSON은 객체의 읽기 형태를 설명한다. 실시간 편집에서는 객체 전체를 교체하지 않고 변경한 속성 단위로 처리해야 한다.

## 물리 타입과 확장 속성

- 물리 타입은 기본 타입, 사용자 정의 타입 참조, 아직 해석되지 않은 직접 입력을 구분하는 안을 제안한다.
- 기본 타입의 길이·정밀도·배열 여부는 구조화하여 UI 편집과 검증에 사용한다.
- 사용자 정의 타입은 타입 정의 객체 ID를 참조하도록 설계한다. PostgreSQL의 사용자 정의 DOMAIN 타입은 업무 설계의 '도메인'과 별도 개념이다.
- 직접 입력은 초안으로 보관할 수 있지만 그대로 SQL에 붙이지 않는다. 지원하는 타입 표현인지 해석·검증하고, 사용자 정의 타입의 생성 또는 사전 존재 조건을 확인한다.
- 자유로운 추가 속성은 공통 / 논리 / 물리 영역별로 둘 수 있다.
- 추가 속성은 기본적으로 메타데이터다. 물리 영역에 넣었다는 이유만으로 SQL 문법이나 제약조건이 되지 않는다.
- 기본값 표현식도 단순 문자열 연결로 출력하지 않고 허용한 SQL 표현과 내보내기 규칙에 따라 검증한다.

## 관계

- 도메인 업무 관계는 출발·도착 도메인 ID, 관계명, 방향, 설명을 가진다.
- 테이블 관계는 안정적인 테이블·컬럼 ID로 연결한다.
- 논리 특성에는 업무상 관계명, 선택성, 관계 차수 등을 둘 수 있다.
- 물리 FK 특성에는 출발·참조 컬럼의 대응, 제약 이름, 삭제·수정 시 동작 등을 둔다.
- 논리 관계만 정의된 상태를 허용한다. 논리 관계 추가만으로 FK를 만들지 않는다.
- 논리 다대다 관계는 그대로 표현할 수 있지만 자동으로 물리 FK로 내보내지 않는다. 물리 구현에는 연결 테이블과 유효한 FK를 명시해야 한다.
- 물리 FK의 컬럼과 참조 키가 물리 적용 범위에 포함되어 있는지, 복합 키의 컬럼 수와 순서가 맞는지 검증한다.

## 화면·댓글 연결

- 캔버스 노드는 모델 객체의 ID를 참조하고 좌표·크기·서식을 가진다.
- 댓글 스레드는 뷰 ID와 객체 ID 또는 빈 공간 좌표를 참조한다.
- 논리 / 물리 보기 전환으로 댓글을 복제하지 않는다.
- 논리 전용 객체의 댓글을 물리 보기에서 열면 해당 객체를 볼 수 있는 보기로 이동할 수 있도록 안내한다.
- 객체를 삭제하면 댓글은 대화 목록에 보존하고 대상 삭제 상태를 표시한다.

## 편집·검증 원칙

1. 논리명 변경 후에도 물리명, 관계, 댓글의 참조는 유지한다.
2. 물리 타입 변경 후에도 논리 타입과 업무 정의는 유지한다.
3. 논리·물리 이름 및 타입을 함께 적용하는 기능은 적용 대상과 변경 내용을 명시한다.
4. 미완성 설계는 저장하되, 오류 진단과 DDL 생성 가능 여부를 표시한다.
5. 논리 전용 객체와 자유 메타데이터를 DDL에서 제외한다.
6. 동일 객체를 수정하는 팀원 간 변경은 속성 단위로 다루고, 삭제·동일 속성 충돌은 별도 정책으로 처리한다.

## 후속 설계 항목

- 서버 저장과 실시간 편집 방식의 최종 선택.
- 논리 타입 사전과 물리 타입 추천 규칙의 범위.
- 키·관계·사용자 정의 타입의 상세 스키마.
- 적용 범위 변경 시 일괄 수정 UI와 삭제·복원 정책.
- 데이터 형식 버전과 향후 마이그레이션 방식.
