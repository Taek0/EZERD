# 자동 저장 브라우저 인수 검증 계획

작성일: 2026-09-15
상태: 실제 5브라우저 검증 완료

## 목적

실제 Chromium 컨텍스트 5개가 같은 프로젝트를 편집하는 조건에서 자동 저장과 객체·속성 단위 동기화의 사용자 계약을 검증한다. 검증은 UI에서 편집을 만들고 다른 화면, 동기화 이력 API, IndexedDB 대기열을 함께 관찰한다. 테스트가 만든 사용자와 프로젝트만 정리하며 기존 데이터나 DB 전체를 삭제하지 않는다.

## 시나리오

1. 서로 다른 5개 브라우저 컨텍스트에서 사용자 세션을 만들고 한 프로젝트를 연다. 최초 참여자가 도메인 두 개와 테이블을 만들면 모든 화면이 1초 목표 안에 수렴하는지 확인한다.
2. 한글 IME 조합 중에는 작업 요청이 발생하지 않고 조합 종료 뒤 약 500ms 입력 정지 또는 blur에서 한 번만 승인되는지 확인한다. 카드 드래그는 이동 중간값을 전송하지 않고 pointerup 뒤 한 번만 승인되는지 확인한다.
3. 한 참여자의 작업 승인 응답을 지연해도 다른 참여자가 서버 승인 이벤트를 먼저 적용하는지 확인한다. 다른 참여자의 마지막 operation 이벤트 하나를 차단한 뒤 서버 head와 누락 이벤트 조회로 따라잡는지 확인한다.
4. 작업 제출 API를 끊은 상태에서 편집하고 IndexedDB에 대기 작업이 생겼는지 확인한다. 같은 컨텍스트를 새로고침한 뒤 로컬 낙관값과 대기 작업이 복원되는지 확인하고, 연결을 회복한 뒤 서버와 다른 참여자에게 반영되는지 확인한다.
5. 승인된 자신의 변경을 실행 취소하고 다시 실행해 모든 참여자가 수렴하는지 확인한다. 다른 사용자가 같은 속성을 후속 변경한 뒤에는 이전 사용자의 undo가 후속값을 덮어쓰지 않는지 이력과 화면으로 확인한다.
6. 서로 다른 속성의 동시 변경은 모두 보존하고 같은 속성의 동시 변경은 마지막 서버 승인값으로 5개 화면이 수렴하는지 확인한다.
7. 개인 조합뷰에서 내용 편집은 공유 원본과 다른 참여자에게 반영되지만 카드 이동은 차단되는지 확인한다. 조합뷰 선택 자체는 다른 참여자의 현재 화면을 바꾸지 않아야 한다.

## 구현 원칙

- 새 스크립트 `scripts/browser-autosync-smoke.mjs`만 추가하고 기존 브라우저 스크립트나 런타임 API는 수정하지 않는다.
- 고유한 접두사와 UUID로 테스트 데이터를 만들고 `finally`에서 해당 프로젝트와 사용자만 명시적으로 삭제한다.
- 요청 수와 서버 이력 sequence를 기준으로 debounce 및 드래그 확정 경계를 검사하고, 화면 문자열만으로 저장 성공을 판단하지 않는다.
- 브라우저 콘솔 오류와 page error를 모으며 실패 시 테스트 프로젝트의 화면 캡처를 남긴다.
- 현재 구현이 시나리오를 지원하지 않으면 검증을 약화하지 않고 실패 원인과 재실행 조건을 작업 기록에 남긴다.

## 완료 기준

- 다섯 컨텍스트가 독립 세션과 clientId를 사용한다.
- 위 일곱 시나리오가 실제 서버, PostgreSQL, WebSocket, IndexedDB를 거쳐 통과한다.
- 테스트 데이터 정리가 개별 ID 조건으로만 수행된다.
- 실행 명령, 통과 결과, 지연 측정값과 남은 한계를 `docs/work-log/2026-09-15-Collaboration-BrowserAutosyncVerification.md`에 기록한다.
