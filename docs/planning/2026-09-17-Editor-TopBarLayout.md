# 편집기 상단바 배치 개선 계획

기록일: 2026-09-17

상태: **방향 합의. 구현 이전이며 이 문서는 구현 완료를 의미하지 않는다.**

대상은 도메인 맵과 도메인 뷰(테이블 캔버스)의 상단바 배치다. 사이드바 내부 구성과 캔버스 조작은 이번 범위가 아니다. 통합 헤더의 기존 결정은 [편집기 통합 도구 헤더](./2026-09-16-Editor-MergedToolbar.md)를 함께 확인한다.

## 1. 현재 구성

한 행에 버튼 12개와 상태 표시 1개가 있고, 세 덩어리로 나뉘며 소유 컴포넌트가 서로 다르다.

| 영역 | 소유 | 내용 |
| --- | --- | --- |
| 왼쪽 | `App.tsx` `.project-title` | `← 갤러리`, `PROJECT / DOMAIN WORKSPACE` 오버라인, 프로젝트명 |
| 가운데 | `Canvas.tsx` `.canvas-toolbar` (portal) | `← 도메인 맵으로`, `/ 도메인명`, `＋ 도메인` 또는 `＋ 테이블`, `도메인 뷰`, `고화질 PNG`, `＋ 메모`, `ENUM`, 구분선, 속성 패널 토글 |
| 오른쪽 | `App.tsx` `.save-controls` | `↶`, `↷`, `핀`, 동기화 상태, `히스토리` |

## 2. 배치가 흩어져 보이는 원인

1. **간격이 한 값이다.** `--editor-gap: clamp(6px, 0.5vw, 8px)`를 `.editor-heading`, `.breadcrumbs`, `.actions`, `.save-controls`가 모두 사용해 그룹 안과 그룹 사이의 간격이 같다. 구분선은 `.toolbar-divider` 하나뿐이라 12개가 등간격으로 읽힌다.
2. **성격이 같은 짝이 갈라져 있다.** 패널 토글 두 개가 가운데와 오른쪽으로 나뉘고 표기도 아이콘과 텍스트로 다르다. 상위로 이동하는 두 버튼 사이에는 프로젝트 제목이 끼어 있다.
3. **생성 버튼이 붙어 있지 않다.** `＋ 테이블`과 `＋ 메모` 사이에 `도메인 뷰`와 `고화질 PNG`가 들어간다.
4. **브레드크럼이 강조 버튼이다.** `.domain-map-return`이 파란 배경과 테두리, 굵기 700, 그림자를 받아 현재 위치 표시가 아니라 주요 행동으로 읽힌다.
5. **뷰에 따라 컨트롤이 나타나고 사라진다.** `← 도메인 맵으로`와 `ENUM`의 유무, `＋ 도메인`과 `＋ 테이블`의 라벨 폭 차이로 가운데 그룹의 폭이 달라져 같은 버튼이 매번 다른 위치에 온다.
6. **소유 컴포넌트가 셋이다.** 어느 그룹에 무엇을 넣을지 규칙을 코드로 강제할 수 없어 새 기능이 가장 가까운 그룹에 붙는다.

## 3. 확정한 방향

### 영역별 역할

| 영역 | 답하는 질문 | 내용 |
| --- | --- | --- |
| 왼쪽 | 어디에 있는가 | 갤러리·프로젝트·도메인 맵·현재 뷰를 잇는 경로 한 줄 |
| 가운데 | 무엇을 만드는가 | `＋ 도메인` 또는 `＋ 테이블`, `＋ 메모` |
| 오른쪽 | 문서 상태와 작업 공간 | `↶ ↷`, 동기화와 히스토리, 패널 토글 두 개 |

- 간격을 두 단계로 나눈다. 그룹 안은 좁게, 그룹 사이는 넓게 둔다.
- 속성 패널 토글을 핀 옆으로 옮겨 두 토글을 같은 표기로 맞춘다.
- 브레드크럼에서 강조 버튼 스타일을 걷어내고 상위 단계는 링크, 현재 단계는 굵게 표시한다.
- 상단바 소유를 한 곳으로 모으고 Canvas는 현재 뷰에서 쓸 수 있는 액션 목록만 전달한다. 뷰와 무관하게 슬롯 수를 고정하는 것이 목표다.

### 도메인 뷰 버튼

도메인 뷰는 서로 다른 도메인의 테이블에 제약 관계를 걸기 위한 작업 공간이며, 전체 맥락을 확인할 때도 사용한다. 특정 단계에서는 자주 사용하므로 상단바에 계속 노출한다. 다만 생성과 성격이 다르므로 `＋ 테이블`과 `＋ 메모` 사이에 두지 않고 분리한다.

같은 버튼이 도메인 맵에서는 조합 뷰 진입으로, 조합 뷰 안에서는 포함 도메인 변경으로 동작한다. 상태에 따라 표시를 나눠 지금 어느 동작인지 드러낸다. 구체적인 라벨 문구는 구현 시 정한다.

브레드크럼 드롭다운으로 흡수하는 안은 채택하지 않는다. 이 동작은 이동이 아니라 문서를 수정하며, 브레드크럼은 부담 없이 누르는 자리이기 때문이다.

### FK 설정 흐름은 유지

출발 컬럼은 사이드바와 컬럼 우클릭에서 지정하고, 대상 테이블은 캔버스 클릭으로 지정하는 현재 분담을 유지한다. 조합 뷰에서 노드를 옮길 수 없어도 FK 지정 중 화면 이동이 가능하므로 작업이 막히지 않는다.

## 4. 함께 확인한 수정 대상

이번 논의에서 발견했으며 상단바 배치와는 별개 단위로 처리한다.

| 항목 | 내용 |
| --- | --- |
| 조합 뷰 경로 삭제 | `applyDomainSelection`이 `upsertCombinedView`가 보존한 관계선 경로를 `relations.filter((r) => r.viewId !== viewId)`로 다시 전부 버린다. 버그로 판단한다. |
| 조합 뷰 단수 고정 | 모델은 `views: CombinedView[]` 배열과 임의 id를 지원하지만 UI가 `doc.views?.[0]`로 되돌아가 사실상 한 개만 쓴다. 이전 버전의 잔재로 판단한다. |
| 조합 뷰 이름 고정 | `upsertCombinedView` 호출이 이름을 `'도메인 뷰'`로 고정해 브레드크럼에 정보가 남지 않는다. 수정 과정의 잔재로 판단한다. |
| 논리·물리 전환 잔재 | `setViewMode`가 없고 `isVisibleInView(c.scope, 'physical', table.scope)`로 물리 고정인데 `.view-mode-switch` 규칙이 `inspector.css`에 남아 있다. 물리 레이어만 남기는 결정에 따라 정리한다. |

## 5. 유지하는 사항

- 단독 도메인 캔버스에는 다른 도메인의 테이블 관계선을 그리지 않는다. 사이드바와 테이블 카드의 참조 표시로 확인한다.
- 조합 뷰의 노드 배치는 원본 도메인 배치에서 파생하며 이동·크기 조절·자동 배치를 막는다.
- 조합 뷰를 삭제해도 거기서 만든 테이블 관계는 남는다.
- 조합 뷰의 도메인 수에 상한을 두지 않는다. 가로 한 줄 배치가 불편해지면 그때 배치 로직을 조정한다.
- 자동 배치는 빈 캔버스 우클릭에서만 실행한다.

## 6. 남은 결정

- 오버플로 메뉴를 도입할지, 도입한다면 `고화질 PNG`와 `ENUM`을 옮길지.
- 도메인 뷰 버튼의 상태별 라벨 문구.
- 간격 분리만 먼저 적용해 체감을 확인할지, 재배치까지 함께 진행할지.

## 7. 검증 기준

- [ ] 그룹 안과 그룹 사이의 간격이 구분된다.
- [ ] 속성과 핀 토글이 같은 표기로 오른쪽에 함께 있다.
- [ ] 도메인 맵과 도메인 뷰를 오갈 때 상단바 슬롯 수와 위치가 유지된다.
- [ ] 브레드크럼이 주요 행동보다 약하게 보인다.
- [ ] 도메인 뷰 버튼의 현재 동작이 표시로 구분된다.
- [ ] 포털 도구의 Delete 방어와 포커스 표시가 유지된다.
