# MySQL physical 제약 정책 계획

- 기준: durable core `9657dd8` 이후. 루트 AGENTS 준수. 담당은 새 mysql-physical-policy.ts/tests, literals.ts/tests의 charset facts 보완, 새 verify-native-mysql-constraints.ts 및 이 계획/작업 로그다. validation/index/UI/queue/계약/DDL compiler는 main 담당이며 수정하지 않는다. git add/commit 하지 않는다.
- MySQL8.4/InnoDB 알려진 charset/collation을 effective column/table 조건으로 해석한다. 문자 수와 선언 최대 byte 수 및 실제 encoded byte를 구분한다. ASCII/utf8mb3/utf8mb4/latin1/binary의 표현 가능 문자와 기본값·ENUM/SET label을 검사하며 미검증 latin1 매핑은 좁은 subset 또는 환경 진단으로 차단한다.
- VARCHAR 단일 선언·전체65535byte row budget, decimal/fixed/bit/variable/ENUM/SET/TEXT reference/null bitmap 공식 식을 분리한다. InnoDB page/row-format 저장 한도와 SQL layer 선언 한도를 혼동하지 않는다. 미검증 타입·환경은 exact bytes/usable로 승격하지 않는다.
- column/table COMMENT의 문자·byte/Unicode 메타데이터 실제 경계를 검증한다. helper는 objectId/path/cause/category/params/severity를 반환하여 main collect/add 및 UI/MCP에서 같은 결과를 소비한다. engineSupported와 usable/coverage false를 분리한다.
- 전용 MySQL container `032eb46e01d610cd0bfbad6127cff0ff47a3c3be648f0a67f3de101d3ecbc282`, label ezerd.qa=native-ddl-20261002, network none/port 없음, 정확한 소유 익명 volume `b64d418edfbd16b0ba710dfb9d9c65b4034dbf59b3da1967756602d88cbfb1d1`→/var/lib/mysql만 inspect 후 require_escalated exec한다. 전문가 metadata 조회 후 UUID 임시 DB만 create/drop한다. 기존 사용자 DB/컨테이너/volume은 변경하지 않는다.
- 공식 MySQL8.4 문서와 실행 fixture 경계를 비교한다. installed charset/collation, lower_case_table_names, page_size/row format 및 strict SQL mode가 다른 경우 보수적 environment/unsupported 진단을 낸다. targeted tests/typecheck/Prettier/실제 SQL evidence를 기록한 후 ready 보고하며 전체 세로 소비/full check/commit은 main 담당이다.
- 기본 정책은 mysql-8.4-innodb-v1의 UTF8MB4/strict SQL mode, x86_64·16KiB·DYNAMIC 검증 조건이다. 옵션이 모두 생략된 table의 기본 charset/collation은 이 profile 가정이며 임의 실행 DB의 다른 기본값을 자동 추론하지 않는다. 실행자는 실제 database 기본값과 명시 옵션을 일치시켜야 한다.
- main 후속 요구에 따라 `mysqlEffectiveColumnTextOptions(table,column?)` 중앙 API로 charset/collationKnown/byteWidth를 제공한다. 검증한5개 charset preset defaults를 같은 resolver에서 해석하고 FK/fulltext/row/literal/DDL이 같은 결과를 사용하도록 main 연결 사양을 기록한다. column CHARSET-only는 해당 charset default collation, 둘 다 생략 시만 table 상속이다. table COLLATE-only에서 추론된 charset과 DDL fallback이 충돌하지 않도록 중앙 해석 결과를 먼저 사용한다.
- latin1 지원은 실제 전체 비NUL cp1252 매핑 검증 이후 확대한다. ENUM/SET의 CI 동등성은 printable ASCII만 검증하고 비ASCII/제어문자 다중 label은 unsupported로 남긴다. 바이너리 collation은 case/Unicode 구별을 유지하며 trailing space label은 DB가 제거하므로 보존 정책에서 차단한다.
- byte budget의 exact는 SQL layer 선언 계산에만 적용한다. InnoDB 전체 record header/MVCC/page overflow의 정확한 추정이나 임의 컬럼 조합의 실행 성공을 보증하지 않는다. legacy/unresolved 타입의 budget은 null이며 명시 unsupported다.
- VIRTUAL follow-up: 기본 VIRTUAL을 일괄 차단하지 않는다. SQL logical 65535bytes 계산에 VIRTUAL 선언 bytes/nullable가 포함되는지 small/huge 단일·이중 VARCHAR, charset 폭/단일 VARCHAR 한도, stored+virtual 조합을 실제 전용 MySQL에서 확인한다. 검증한 SQL budget 식 또는 안전한 upper bound만 허용하고 물리 stored layout과 구분한다. 미검증·초대형 조합은 명시 진단을 유지한다.
- InnoDB1017 column 한도는 일반·VIRTUAL 및 functional index의 hidden virtual column을 포함해 보수적으로 센다. 일반/명시 VIRTUAL boundary와 functional key part의 추가 컬럼 boundary를 실제 실행하고, AST의 functional 결과 타입/논리 byte layout이 미검증이면 그 부분은 별도 unsupported로 남긴다. 계획·코드·QA·work-log만 담당 범위에서 갱신하며 main validator/DDL은 수정하지 않는다.
